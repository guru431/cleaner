| | |
|---|---|
| Статус | черновик, на согласовании |
| Дата | 13.10.2026 |
| Требования | [TZ.md](../../../TZ.md) |

Документ описывает, как устроена система, удовлетворяющая ТЗ: части, их границы и интерфейсы, данные, алгоритмы замены и восстановления, порядок проверки. Номера `FR-…`, `SEC-…`, `NFR-…`, `QA-…` отсылают к ТЗ.

## 1. Основные решения

1. **Собственное приложение на Python**: FastAPI, серверные шаблоны Jinja2 с обычными формами и одним небольшим скриптом, SQLite для хранения. Работает службой systemd на сервере `example` (Ubuntu 24.04, Python 3.12); разработка и быстрые тесты — на Windows.
2. **Одно ядро очистки и восстановления** без сетевого доступа. Веб-интерфейс, командная строка и (в будущем) прокси — тонкие входы в это ядро.
3. **Единственный модуль выхода в сеть** принимает только объект, собранный ядром, и сам повторяет проверку утечек.
4. **Пять слоёв распознавания** дают фрагменты; фрагменты объединяются, а не голосуют.
5. **Замена зависит от типа**: метки для людей, организаций и учётных записей; подмены с сохранением формата для сети.
6. **Восстановление — точное**, без нечёткого сопоставления; искажения оформления меток разбираются по строгому шаблону.
7. **Шифрование по ключу на чат**; главный ключ служба получает при запуске из файла, доступного только root.
8. **Размещение на `example` с исключением из запрета исходящих** (решение владельца от 13.10.2026): Cleaner — единственная служба сервера с выходом в интернет, и только на порт 443.

Не используются: Presidio как каркас (распознаватели привязаны к одному языку, слияние фрагментов не подходит), LiteLLM (инцидент с пакетом в марте 2026 года и незакрытые ошибки восстановления), SQLCipher (шифрует файл целиком и не позволяет стереть ключ отдельного чата), реалистичные вымышленные имена вместо меток (скрывают от человека пропуски распознавания).

## 2. Архитектура

```
 Браузер ──HTTPS──▶ web ─────────────────────────────────────────────┐
                     │                                               │
                     ▼                                               ▼
                  pipeline ◀──▶ storage (SQLite, шифрование)        jobs
                     │
        ┌────────────┼──────────────┬───────────────┐
        ▼            ▼              ▼               ▼
     detect/*     entities/*     restore        leakcheck
        │
        ├── слой 4: локальные модели (CPU, без сети)
        └── слой 5: local_llm ──HTTP──▶ локальная LLM (петлевой или частный адрес)

     ingest (Docling, распознавание текста) — без сети

     egress.cloud ──HTTPS──▶ облачный провайдер
          ▲
          └── только OutgoingContext из pipeline.build_outgoing()
```

### Границы доверия

| Зона | Что видит оригиналы | Сеть |
|---|---|---|
| `core`, `ingest`, `storage` | да | нет |
| `local_llm` | да | только адрес локальной модели |
| `egress` | нет — только очищенный текст | только адреса подключений |
| `web` | да (показывает пользователю) | входящие соединения |

### Правила зависимостей

- Сетевые библиотеки (`httpx`, `requests`, `urllib.request`, `aiohttp`, `socket`) импортируются только в `cleaner/egress/` и `cleaner/local_llm.py`. Это проверяет тест, разбирающий импорты всех модулей пакета (SEC-1).
- При старте процесса выставляются `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1`, чтобы библиотеки моделей не обращались в интернет (NFR-2).
- `core` не зависит от `web`, `storage`, `egress`. Состояние чата `core` получает и возвращает объектами в памяти; чтение и запись выполняет `storage`.

## 4. Данные

SQLite, режим WAL, `PRAGMA secure_delete=ON`, `PRAGMA foreign_keys=ON`. Идентификаторы строк — UUID, создаются приложением. Столбцы с суффиксом `_enc` зашифрованы (раздел 12).

| Таблица | Столбцы | Назначение |
|---|---|---|
| `users` | `id`, `login`, `password_hash`, `role`, `disabled`, `created_at` | Учётные записи |
| `sessions` | `token_hash`, `user_id`, `csrf`, `created_at`, `last_seen_at` | Сессии входа и токен форм |
| `chats` | `id`, `user_id`, `title_enc`, `dek_wrapped`, `state_enc`, `version`, `label_style`, `layers` (JSON: какие слои отключены), `provider_id`, `model`, `created_at`, `updated_at` | Чат, его ключ и состояние замен |
| `items` | `id`, `chat_id`, `seq`, `kind` (`input` / `answer`), `source` (`paste` / `file` / `instruction` / `api` / `pasted_answer` / `local`), `original_enc`, `sanitized_enc`, `spans` (JSON: позиции, id сущности, источники — без значений), `notices` (JSON), `exposed` (JSON: id сущностей, открытых в выданном тексте, FR-6.8), `status` (`queued` / `running` / `done` / `failed` / `partial`), `meta` (JSON: вид файла, страницы, слои, подключение и модель ответа, постоянная причина отказа — без текста), `created_at` | Элементы чата. Для ответа `original_enc` — текст, как он пришёл от модели. Инструкция пользователя для модели (FR-8.5) — входной элемент `instruction`: она проходит те же слои и тот же экран проверки |
| `dictionary` | `id`, `list` (`always` / `never`), `type`, `value_enc`, `aliases_enc`, `comment_enc` | Словарь организации |
| `patterns` | `id`, `name`, `regex`, `type`, `enabled` | Пользовательские шаблоны |
| `policies` | `type`, `policy` | Политики типов |
| `providers` | `id`, `name`, `protocol`, `base_url`, `auth_style`, `api_key_enc`, `models`, `max_tokens`, `extra_body`, `enabled` | Подключения |
| `settings` | `key`, `value` | Адрес и модель локальной LLM, вид метки по умолчанию, обёрнутый общий ключ |
| `gold` | `id`, `user_id`, `text_enc`, `spans_enc`, `created_at` | Эталонные примеры: копия текста с разметкой (тип, номер сущности в примере, происхождение) под общим ключом; после удаления чата пример остаётся в наборе. Открытые наборы QA-4 скачивает сценарий разработки `scripts/fetch_open_sets.py` в JSONL, `cleaner eval --jsonl` их измеряет |
| `audit` | `id`, `ts`, `user_id`, `chat_id`, `event`, `details` (JSON без оригиналов) | Журнал |

Удаление чата удаляет его строки каскадом, включая `dek_wrapped` (FR-1.4). Исходные файлы не сохраняются (FR-2.7).

Столбцы, нужные только поздним этапам, — `chats.label_style`, `layers`, `provider_id`, `model`, `system_enc`, `items.source`, `status`, `meta` — и таблицы `providers` и `gold` добавляются миграцией вместе с этими этапами; схема этапа 1 их не содержит (вид метки на этапе 1 хранится в состоянии чата).

Миграции — нумерованные файлы `cleaner/storage/migrations/NNNN_*.sql`, каждый своей транзакцией; `schema.sql` остаётся версией 1, номер схемы — номер последнего файла. Версия 2 (план «2+4») добавляет `items.source`, `status`, `meta`, `model_spans` (находки слоёв 4–5: позиции, тип, источник, без значений), `risk_status`, `risk_enc` (результат проверки остаточного риска, зашифрован: верная догадка модели — это оригинал), `chats.layers` и таблицу `gold` со столбцом `user_id`. Версия 3 (план «3») — таблицу `providers` (ключ под общим ключом) и `chats.provider_id`, `model`; столбца `system_enc` нет: инструкция пользователя — элемент чата.

**Состояние замен чата хранится целиком** — объект `ChatState` ядра, сериализованный в JSON и зашифрованный ключом чата (`chats.state_enc`): сущности с написаниями и значениями для восстановления, таблица замен с оригиналами подмен, выданные номера (`issued`), счётчики, подсети IPv6, псевдонимы объединений, правила пользователя, посторонние метки. Отдельных таблиц для них нет:

- потеря любого из этих полей (например, `issued` или счётчиков) привела бы к выдаче других замен для уже известных сущностей — целиком состояние не расходится само с собой;
- новое поле ядра сохраняется без миграции схемы;
- обновление атомарно: запрос загружает состояние, ядро меняет его в памяти, и только после успешной очистки состояние и новый элемент записываются одной транзакцией; исключение отбрасывает изменённый объект целиком;
- одновременная запись двух запросов в один чат отсекается полем `version` (оптимистическая блокировка): второй получает отказ и повторяет очистку на свежем состоянии.

Таблица сущностей на экране чата строится из этого объекта после расшифровки.

## 5. Конвейер очистки

### 5.1. Типы

```python
class Span:            # фрагмент оригинала
    start: int         # позиции в кодовых точках Unicode
    end: int
    type: EntityType
    source: str        # rules | secrets | infra | dict | ner | llm | manual
    score: float       # 1.0 у детерминированных слоёв
    validated: bool    # подтверждён контрольной суммой или строгим форматом

class Detector(Protocol):
    name: str
    def detect(self, text: str, ctx: DetectContext) -> list[Span]: ...

class SanitizeResult:
    sanitized: str
    spans: list[ResolvedSpan]      # фрагмент оригинала + сущность + выданная замена
    notices: list[Notice]          # surrogate_in_input | foreign_label
    leaks: list[Leak]              # находки проверки утечек (раздел 8)
    blocked: list[ResolvedSpan]    # фрагменты типов с политикой «блокировать»
    deliverable: bool              # нет ни утечек, ни блокировок
```

`DetectContext` несёт словарь организации, пользовательские шаблоны, известные формы сущностей чата, правила чата и политики типов.

`pipeline.sanitize(chat: ChatState, text: str, settings: Settings) -> SanitizeResult` выполняет шаги 5.2–5.10 и обновляет `ChatState` новыми сущностями и заменами. `Settings` — общие для всех чатов словарь организации, шаблоны и политики типов. Любое исключение в любом шаге прерывает очистку целиком (FR-3.7).

### 5.2. Слой 1 — правила (`rules.py`)

Каждое правило — шаблон, необязательная проверка и необязательное требование контекста.

| Тип | Шаблон | Проверка | Контекст |
|---|---|---|---|
| `EMAIL` | адрес с `@` и доменом | — | не нужен |
| `PHONE` | `+7`/`8` и 10 цифр с любыми разделителями; международная запись с `+` | число цифр | для «голых» 10–11 цифр — слова «тел», «моб», `phone` |
| `CARD` | 13–19 цифр с пробелами или дефисами | алгоритм Луна | не нужен |
| `INN` | 10 или 12 цифр | контрольные разряды | не нужен |
| `SNILS` | 11 цифр, в том числе вида `XXX-XXX-XXX YY` | контрольное число | не нужен |
| `OGRN` | 13 или 15 цифр | контрольный разряд | не нужен |
| `BANK_ACCOUNT` | 20 цифр; IBAN | ключ счёта при найденном рядом БИК; для IBAN — остаток по модулю 97 | без БИК — слова «счёт», «р/с», «к/с» |
| `KPP` | 9 цифр | — | «КПП» |
| `PASSPORT` | серия и номер, 10 цифр с пробелами | — | «паспорт», «серия», «выдан» |
| `OMS` | 16 цифр | — | «полис», «ОМС» |
| `BIRTHDATE` | дата | допустимость даты | «дата рождения», «г.р.», «д.р.», `born`, `DOB` |

Запись «логин@хост» и «логин:пароль@хост» сразу после `схема://` (`https://ivanov@git.contoso.ru/…`, `ssh://ivanov@srv-db01`, `mongodb://petrov:…@db01…`) — не e-mail, а учётная запись: логин помечается `ACCOUNT` отдельным правилом, независимо от того, каким знаком кончается пароль и есть ли у хоста точка; пароль находит слой 2 (и без логина: `redis://:пароль@хост`), хост — слой 3. Со знаками `?#=` до `@` это уже параметры адреса, и запись — e-mail. Служебные входы и подстановки (`git`, `postgres`, `app`, `sa`, `login`, `имя` и подобные, а также стандартные учётные записи) не помечаются; это свой список правила, а не общий список стандартных учётных записей, иначе `SA\petrov` перестал бы скрываться.

Число без контрольной суммы и без контекста не помечается. Десятизначное число, случайно прошедшее проверку ИНН (примерно одно из десяти), будет скрыто: это осознанная плата за полноту.

Все проверки контрольных сумм реализованы в `validators.py` без внешних библиотек: это около сорока строк, и так на одну зависимость меньше. Алгоритмы в исследовании получены из вторичных источников, согласных между собой; каждый покрывается тестом на известных действительных и недействительных номерах.

### 5.3. Слой 2 — секреты (`secrets.py`)

Две группы правил.

**По виду значения:**

- блоки приватных ключей PEM;
- JWT;
- токены с известными префиксами — набор правил `detect-secrets`, вызываемый как библиотека на строках текста, с выключенной проверкой у провайдера (FR-3.9). Выключены: правила по энтропии и `KeywordDetector` (шумят на обычном тексте), `IPPublicDetector` (адреса — работа слоя 3, они получают подмену и восстанавливаются), `NpmDetector`, `JwtTokenDetector` и `OpenAIDetector` (квадратичны на длинной строке; их токены находят собственные шаблоны). Перед правилами IBM, Cloudant и Softlayer серии пробелов сжимаются: на них эти правила кубичны.

**По контексту** (значение скрывается независимо от того, насколько оно «случайно»):

- `ключ = значение` и `ключ: значение`, где имя ключа содержит `password`, `passwd`, `pwd`, `pass`, `secret`, `token`, `api_key`, `access_key`, `credential`, «пароль»;
- параметры командной строки `--password значение`, `-Password значение`, `/p:значение`;
- учётные данные в адресе: `scheme://user:password@host`;
- поля `Password=…;` и `Pwd=…;` в строках подключения;
- в свободном тексте — слово после «пароль», «пароль:», `password is`;
- пароль на своём месте в известных командах: `net use \\узел\ресурс <пароль> /user:…`, `mysql -p<пароль>` и `mariadb` (только слитно: `-P` — порт), `sshpass -p <пароль>`, `<add key="…Password" value="…"/>` в `web.config`.

Скрывается только значение, имя ключа остаётся. Пароли в свободном тексте без ключевого слова этот слой не находит; их ищет слой 5.

Уточнения правил по контексту:

- стоп-список ключей, которые только похожи на секрет, не отменяет ключ, оканчивающийся словом секрета (`token`, `secret`, `key`, `password`, `pwd`, `pass`, `passphrase`, `credential`): `bypass_token`, `password_reset_token` — секреты;
- имя ключа ограничено 64 знаками по обе стороны от слова секрета;
- после ключа или параметра значением считается строка от двух знаков; «да», «нет», `ok` значениями не считаются; в значении без кавычек имя следующего поля не содержит пробелов (`pwd=Qw,er7y retries=3` — значение `Qw,er7y`), кроме полей строки подключения ADO.NET: `;` и слова с заглавной буквы через пробел перед `=` (`;Persist Security Info=`) значение заканчивают;
- значением не считаются: значение, равное составному имени ключа (`cancellationToken: cancellationToken`), вызов команды PowerShell вида `Глагол-Существительное`, число под ключом, где слово секрета — только `token` (счётчики `max_new_tokens: 1024`; цена — числовой одноразовый код `verification_token: 482913` не скрывается), путь после `PWD=`/`OLDPWD=`, свойство MSBuild `/p:Имя=Значение`, следующий флаг (`--password --verbose`), русское слово через дефис после «пароль» («по-прежнему»), обычное слово после `bearer`;
- после тире («Пароль — sunflower») значение отбрасывается, только если это слово-связка («это», `is`, …) или за ним продолжается фраза, а само оно на пароль не похоже.

### 5.4. Слой 3 — инфраструктура и словари (`infra.py`, `dictionary.py`)

- **IP.** Кандидаты разбираются модулем `ipaddress`; строки, которые им не разбираются, отбрасываются. Запись с длиной префикса (`10.1.2.0/24`) — один фрагмент.
- **MAC.** Шесть пар шестнадцатеричных цифр с `:` или `-`, запись Cisco с точками.
- **Доменные имена и хосты с точками.** Имя помечается, если его последняя часть — действующий домен верхнего уровня (по встроенной копии списка публичных суффиксов, библиотека `tldextract` без обращения к сети) или внутренний суффикс из списка (`local`, `lan`, `corp`, `internal`, `intra`, `home`, `localdomain`, `ad`). Не помечаются:
  - имена из списков «никогда не скрывать» и общеизвестных доменов, включая их поддомены;
  - зарезервированные имена IANA (`example.*`, `localhost`, `test`, `invalid`);
  - имена, похожие на файл или на код, — они помечаются только в сетевом контексте (после `://`, `\\`, в параметре команды) или по словарю:
    - последняя часть совпадает с расширением файла или частым словом в коде (`md`, `py`, `zip`, `name`, `id`, `run` и подобные — встроенный список);
    - в части имени смешан регистр (`System.Net`);
    - все части, кроме последней, — числа (`1.2.3.dev`);
    - сразу за именем стоит открывающая скобка (`re.search(`).
- **Ветки реестра** (`HKLM`, `HKCU`, `HKCR`, `HKU`, `HKCC`) перед `\` — не домен и не учётная запись: `reg query HKLM\Software` остаётся как есть.
- **Адрес IPv4 с ведущими нулями** (`010.001.002.005`) читается десятичным и сводится к той же сущности и той же подмене, что `10.1.2.5`; восстанавливается в простой записи. Совпадение подмены с адресом текста проверяется по адресу, а не по записи: `2001:0db8:0001::0001` в тексте не даст подмены `2001:db8:1::1`.
- **Имя под выданным фиктивным доменом** (`srv-db02.domain-1.example` — настоящий узел, вписанный пользователем под домен чата) — узел: части перед выданным доменом скрываются, если сами не выданные замены (`host-1.domain-1.example` остаётся как есть), хотя `.example` в списке общеизвестных.
- **Хосты без точек.** Находятся по словарю, по пользовательским шаблонам и по структурным признакам: `\\HOST\ресурс`, `HOST$`, значение параметров `-ComputerName`, `-Server`, `-cn` и `/S` — последнего только у команд, которые принимают имя компьютера (`schtasks`, `systeminfo`, `tasklist`, `taskkill`, `gpresult`, `getmac`, `driverquery`, `eventcreate`, `openfiles`, `waitfor`, `setx`, `takeown`): у `dir`, `xcopy`, `reg` и других `/s` значит «с подкаталогами». Буква диска после ключа хостом не считается.
- **Учётные записи.** `DOMAIN\login`; имя профиля в путях `C:\Users\<имя>\`, `/home/<имя>/`; значения из словаря. Имя профиля из нескольких слов (`C:\Users\Иван Петров`, слова и через дефис — `Petrov-Vodkin`) берётся целиком и перед разделителем пути, и перед кавычкой, знаком препинания или концом строки; цена — в «`C:\Users\ivanov лежит.`» обе части скрываются одной заменой. Стандартные имена (`Administrator`, `Администратор`, `Guest`, `SYSTEM`, `Public`, `Default`, `root`) не помечаются.
- **SID.** `S-1-5-21-…`; общеизвестные SID не помечаются.
- **DN.** Последовательности `CN=…,OU=…,DC=…` — один фрагмент.
- **Словарь организации.** Каждое значение и его варианты из списка «всегда скрывать» ищутся без учёта регистра, «ё/е», вида пробелов между словами (двойной, неразрывный, перевод строки) и формы записи букв (NFC); варианты одной записи словаря получают одну замену. Границы зависят от типа:
  - для типов с подменой (`IP`, `MAC`, `HOST`, `DOMAIN`, `SID`) рядом не должно быть букв, цифр, `_` и `-`;
  - для остальных типов рядом не должно быть букв — так логин `ivanov` находится и в `ivanov_backup`, но не в `ivanova`.
- **Известные значения чата.** Так же ищутся все написания уже найденных сущностей чата (FR-3.4). Короткая часть имени узла становится искомым написанием, только если она встретилась отдельно или содержит цифру либо дефис: иначе слово вроде `portal` скрывалось бы во всём тексте.
- **Правила пользователя.** Значение, которое пользователь выделил и велел скрывать, ищется в любом месте текста, без оглядки на границы.
- **Пользовательские шаблоны.** Выполняются с ограничением времени на одно выражение.

Правила для хостов без точек и учётных записей — эвристики: опубликованных измерений их точности нет. Их качество видно по счётчикам QA-2.

### 5.5. Слой 4 — модели распознавания имён (`ner.py`)

- Русский текст: `redmadrobot-rnd/rubert-base-pii-ner` (Apache-2.0), скользящее окно 512 токенов с шагом 128.
- Английский и смешанный текст: `knowledgator/gliner-pii-base-v1.0` (Apache-2.0).
- Обе модели проходят по всему тексту; находки складываются. Порог уверенности низкий (0,25) — в пользу полноты.
- Используются типы `PERSON`, `ORG`, `ADDRESS`; остальные типы моделей приводятся к типам ТЗ или отбрасываются, если их надёжнее находят слои 1–3.
- Модели загружаются один раз при первом обращении и выполняются по одной, чтобы не занимать все ядра.
- Исполнение — на процессоре. Формат (ONNX или PyTorch) выбирается проверкой в начале этапа 2 по совпадению качества и скорости.
- Подробности (план «2+4»): `rubert` — конвейер `transformers` `token-classification` с `aggregation_strategy="simple"` и `stride=128`, порог 0,25 — к оценке найденной группы, обрывки одной сущности склеиваются; GLiNER — окна по 200 слов с перекрытием 40, метки `name`, `organization`, `location address`. Обе модели — PyTorch, 4 потока, общая блокировка. Если не укладываются в NFR-4 — `rubert` с динамическим квантованием int8 и GLiNER из ONNX-файла quint8 его репозитория (`onnxruntime`); квантовать GLiNER средствами `torch` нельзя — замер дал ноль находок.
- `ADDRESS` из частей адреса русской модели выдаётся, только если среди соседних частей есть улица или дом: город или страна сами по себе не скрываются. Номера водительского удостоверения, военного билета и свидетельства о рождении становятся `PASSPORT`.
- У русской модели нет метки организации, а GLiNER обучен на английском, поэтому русские организации находит детерминированное правило слоя 1 (`detect/orgs.py`): организационно-правовая форма и название в кавычках.
- Находка `ORG` в нижнем регистре, состоящая только из обычных существительных словаря `pymorphy3` (предлоги, союзы и частицы между ними допускаются), отбрасывается: «из бухгалтерии», «отдел кадров» — не организации. Заглавная буква, цифра, прилагательное или неизвестное слово находку оставляют. Точность `ORG` на открытых наборах выросла вдвое (`hivetrace` 0,016 → 0,033, `jayguard` 0,059 → 0,100) при неизменной полноте классов QA-3; мерить её всерьёз можно только на наборе с разметкой организаций — в открытых её нет.
- Находка слоя 4, похожая на пароль (три строчные буквы прямо перед цифрой в слове, «sunflower77»), при включённом слое 5 отбрасывается: слой 5 видит текст, уже очищенный слоями 1–4, и иначе не может дать ей тип `SECRET`. Без слоя 5 она остаётся — отбросить её значило бы открыть сам пароль.
- Находки слоёв 4 и 5 считаются один раз на элемент и хранятся в нём (`items.model_spans`). Повторная очистка после правки на экране проверки использует их и модели не вызывает; заново модели вызывает только «Очистить заново».
- На Linux `torch` ставится сборкой `+cpu` с индекса PyTorch: сборка PyPI тянет пакеты CUDA, а видеокарта сервера занята языковой моделью.

### 5.6. Слой 5 — локальная LLM (`detect/llm.py`)

1. Текст, уже очищенный слоями 1–4, делится на части по 6 000 знаков с перекрытием 500.
2. Для каждой части модели задаётся вопрос: какие строки здесь ещё выдают человека, организацию, учётные данные или инфраструктуру. Ответ ограничен схемой JSON: список объектов `{"text": дословная строка, "type": один из типов}`. Температура 0.
3. Строка принимается, только если она дословно присутствует во входной части и не содержит уже выданных замен. Позиции находит код, а не модель.
4. Обрыв ответа по лимиту длины и невалидный JSON — ошибка: часть повторяется один раз с половинным размером, затем очистка прерывается.
5. Слой 5 запускается один раз — после того как слои 1–4 сошлись, — и проходы 5.2–5.8 повторяются с его находками. Корень схемы ответа — объект `{"items": [...]}`; обёртки кода и блок `<think>` отбрасываются. Передавать ли схему параметром `response_format` или только текстом запроса — настройка, её значение выбирает проверка начала этапа 4.
6. Включение слоёв 4 и 5: в чате хранится только явное решение пользователя (`chats.layers`), без него действует умолчание администратора — слой 4 включён, слой 5 выключен, пока измерение не покажет прироста полноты (раздел 19).

### 5.7. Объединение (`merge.py`)

1. Отбрасываются фрагменты типов с политикой «не искать».
2. Фрагменты сортируются по началу; пересекающиеся сливаются в один интервал.
3. Соседние части имени (фамилия, имя, отчество, инициалы), разделённые только пробелами, сливаются в один `PERSON`; «точка с пробелом» допускается лишь после одиночной буквы — инициала («И. Иванов»), иначе двое на стыке предложений («…Петров Сергей. Иванов Иван…») стали бы одним. Этот шаг появляется на этапе 2 вместе с разбором имён.
4. Тип слитого фрагмента — старший по порядку: правило пользователя, `SECRET`, фрагмент с `validated`, инфраструктура и словарь, слой 4, слой 5 (FR-3.3). Уверенность на отбрасывание не влияет.
5. Удаляются фрагменты, текст которых точно совпадает со значением правила `unmask` чата или списка «никогда не скрывать» (FR-3.6). Фрагменты из правил `mask` при этом не удаляются.

### 5.8. Сопоставление с сущностями (`resolve.py`)

Для каждого фрагмента вычисляется канонический ключ; фрагмент относится к сущности чата с тем же типом и ключом либо создаёт новую.

| Тип | Канонический ключ |
|---|---|
| `EMAIL` | адрес в нижнем регистре |
| `PHONE` | только цифры; ведущая `8` российского номера заменяется на `7` |
| Номера (`INN`, `CARD` и другие) | только цифры |
| `PERSON` | раздел 5.9 |
| `ORG` | нижний регистр, без кавычек и организационно-правовой формы, русские слова в начальной форме |
| `ADDRESS` | нижний регистр, без знаков препинания, одиночные пробелы |
| `HOST` | первая часть имени в нижнем регистре |
| `DOMAIN` | имя в нижнем регистре |
| `IP` | адрес в каноническом виде |
| `MAC` | 12 шестнадцатеричных цифр |
| `ACCOUNT` | имя входа в нижнем регистре без домена |
| `SID` | идентификатор домена (три числа после `S-1-5-21`) |
| `SECRET`, `DN`, `TERM` | значение как есть; для `TERM` — без учёта регистра |

Запись словаря организации с несколькими вариантами написания задаёт одну сущность: все варианты ведут к одному ключу.

### 5.9. Имена (`names.py`, этап 2)

- Слова упоминания разбираются `pymorphy3`: определяется роль (фамилия, имя, отчество) и начальная форма. Инициал — буква с точкой. Слова латиницей сравниваются без учёта регистра.
- Упоминание совместимо с сущностью, если каждая его часть согласуется с ней: начальные формы совпадают, инициал совпадает с первой буквой имени или отчества.
- Упоминание присоединяется к сущности, если совместимая сущность в чате ровно одна; иначе создаётся новая. Более полное упоминание дополняет сущность недостающими частями.
- Следствие: мужчина и женщина с одной фамилией, упомянутые только по фамилии, сольются в одну сущность. Это ошибка полезности, а не приватности; исправляется вручную (FR-6.4).
- Значение для восстановления — самое полное написание, встреченное в именительном падеже; если такого не было — самое полное написание как есть. Пользователь может его изменить, и его значение закрепляется.
- Разборы `pymorphy3` во множественном числе не учитываются: «Петров» — ещё и родительный падеж множественного числа имени «Пётр», и без этого фамилия совпадала бы с именем. Написание, уже отнесённое к сущности, за ней и остаётся — иначе появившийся позже тёзка делал бы его неоднозначным.
- Сущность хранит части ФИО по ролям (`parts`), прочие слова имени (`words`) и полноту значения для восстановления (`restore_rank`).

До этапа 2 люди попадают в чат только из словаря и ручных правил и сопоставляются по перечисленным вариантам написания.

### 5.10. Построение очищенного текста

Для каждого фрагмента сохраняется строка `spans` с позицией в оригинале, сущностью и выданной заменой — по ним строится подсветка обеих панелей. Очищенный текст проходит проверку утечек (раздел 8) до выдачи пользователю.

Шаги 5.2–5.8 выполняются до трёх раз: написания сущностей, найденных в первом проходе, во втором ищутся в том же тексте. Так короткое имя узла связывается с полным, даже если оба впервые встретились в одном тексте.

Замены этого чата, встретившиеся во входном тексте, не трогаются; пользователь получает уведомление. Различить подмену адреса и настоящий адрес, совпавший с ней, по тексту нельзя — совпавший адрес считается подменой.

Составная запись, задевшая выданную замену («`petrov@domain-1.example`», «`host-1.fabrikam.ru`», «`CN=host-1,OU=Servers,DC=fabrikam,DC=local`»), не отбрасывается целиком: часть вне замены скрывается — имя до `@` как `ACCOUNT`, часть имени узла как `HOST` или `DOMAIN`, остаток DN как `DN`. Не скрываются служебные ящики RFC 2142 (`postmaster`, `abuse` и другие), стандартные учётные записи и общеизвестные части (`example`, `www`). Повторная вставка уже очищенного текста ничего не меняет.

Повторная очистка того же оригинала при неизменных правилах даёт тот же результат. После изменения правил:

- элементы, не отправленные по API, очищаются заново;
- элементы, отправленные по API, хранят очищенный текст в том виде, в каком он ушёл;
- в обоих случаях элемент, в прежнем очищенном тексте которого было открыто значение, которое теперь скрывается, получает пометку (FR-6.8).

## 6. Замены

### 6.1. Метки (`labels.py`)

- Вид: `<ТИП_N>` или `[[ТИП_N]]` — по настройке, сохранённой в чате (FR-5.10). `N` — порядковый номер сущности данного типа в чате.
- Метка не содержит пробелов. Знак подчёркивания внутри не даёт Markdown принять `<PERSON_1>` за HTML-тег.
- Строки входного текста, совпадающие по виду с меткой: если такая замена есть в таблице чата — остаётся как есть (FR-5.9); если нет — выдаётся предупреждение (FR-5.8), а строка запоминается как посторонняя и при восстановлении не трогается.

### 6.2. IPv4 (`netmap.py`)

Классификация — по `ipaddress` и реестрам IANA.

| Класс | Замена |
|---|---|
| Петлевые, `0.0.0.0/8`, `255.255.255.255`, групповые, `169.254.0.0/16`, зарезервированные, документационные диапазоны, маски подсетей | не меняются |
| Частные `10/8`, `172.16/12`, `192.168/16` и `100.64/10` | перестановка с сохранением префиксов |
| Остальные (публичные) | по порядку появления: `203.0.113.1…254`, затем `198.51.100.x`, затем `192.0.2.x`; после 762 адресов — метка `<IP_N>` |

Перестановка для частных адресов:

```python
def map_private(addr: int, fixed_bits: int, key: bytes) -> int:
    out = addr & prefix_mask(fixed_bits)          # префикс диапазона не меняется
    for i in range(fixed_bits, 24):               # биты до границы /24
        prefix = addr >> (32 - i)                 # первые i бит оригинала
        flip = hmac_sha256(key, bytes([i]) + prefix.to_bytes(4, "big"))[0] & 1
        out |= (((addr >> (31 - i)) & 1) ^ flip) << (31 - i)
    return out | (addr & 0xFF)                    # последний октет сохраняется
```

`fixed_bits` равно 8, 12, 16 и 10 для четырёх диапазонов. `key` выводится из ключа чата (раздел 12), поэтому в разных чатах один адрес получает разные подмены.

Свойства, проверяемые тестами:

- два адреса с общими первыми `k` битами (`k ≤ 24`) получают подмены с общими первыми `k` битами — подсети сохраняются (FR-5.4);
- преобразование взаимно однозначно внутри диапазона и обратимо;
- диапазон и последний октет сохраняются.

Запись с длиной префикса: адрес преобразуется как обычно; если в оригинале биты после префикса были нулевыми, они обнуляются и в подмене, чтобы адрес сети остался адресом сети. Выданная строка записывается в `surrogates`.

Подмена может случайно совпасть с другим настоящим адресом чата (в диапазоне `192.168/16` это вероятно). Настоящий адрес при этом сам заменён, поэтому восстановление остаётся однозначным, а на экране проверки подмена выделена цветом. Если же совпавший настоящий адрес оставлен открытым (список «никогда не скрывать»), вместо подмены выдаётся метка `<IP_N>` (FR-5.7).

### 6.3. IPv6 (`netmap.py`)

- Не меняются: `::1`, `::`, групповые, `2001:db8::/32`.
- Локальные адреса канала (`fe80::/10`): префикс сохраняется, идентификатор интерфейса заменяется порядковым номером.
- Остальные: каждой встреченной подсети `/64` по порядку назначается `2001:db8:N::/64`; идентификатор интерфейса заменяется порядковым номером. Принадлежность одной `/64` сохраняется, отношения более коротких префиксов — нет.

### 6.4. Хосты и домены (`hostmap.py`)

Имя разбирается на регистрируемую часть (домен с публичным суффиксом; для внутренних суффиксов — две последние части) и части слева от неё.

- Регистрируемая часть — сущность `DOMAIN` — заменяется на `domain-N.example`.
- Каждая часть слева получает псевдоним из общей для чата таблицы «часть → псевдоним». Псевдоним назначается при первом появлении и больше не меняется: `host-N`, если часть впервые встретилась крайней слева или как имя без точек, и `sub-N`, если впервые встретилась в середине. Номер — общий счётчик частей.
- Части из списка служебных имён (`www`, `mail`, `smtp`, `vpn`, `ns1`, `ldap`, `_tcp` и подобные) не заменяются.
- В таблицу замен записываются и части, и составное имя целиком: так восстановление отличает имя из запроса от имени, которое модель составила сама.

Пример: `srv-dc01.msk.corp.contoso.ru` → `host-1.sub-2.sub-3.domain-1.example`; позже `SRV-DC01` → `HOST-1`, `corp.contoso.ru` → `sub-3.domain-1.example`.

- Имя без точек, написанное заглавными буквами, получает подмену заглавными.
- NetBIOS-имя домена получает подмену `DOMAIN-N`; если в словаре оно записано вариантом DNS-домена, номер у них общий.
- Номер пропускается, если строка подмены уже встречается в оригиналах чата (FR-5.7).

### 6.5. MAC и SID (`macsid.py`)

- MAC: `N`-й адрес чата → `02:00:00:xx:xx:xx` (номер в трёх последних байтах), в том же виде записи, что оригинал. `ff:ff:ff:ff:ff:ff` и нулевой адрес не меняются.
- SID: три числа идентификатора домена заменяются фиктивной тройкой, одной на домен; завершающий номер (RID) сохраняется.

### 6.6. Секреты

`SECRET` получает метку `<SECRET_N>`; значение записывается в таблицу чата (FR-4.3). При политике «скрывать без восстановления» метка в ответе не заменяется.

## 7. Восстановление (`restore.py`)

```python
def restore(chat: ChatState, answer: str, settings: Settings) -> RestoreResult   # chat не меняется
# RestoreResult.text      — восстановленный текст
# RestoreResult.segments  — разметка для выделения: restored | altered | derived |
#                           unknown | kept_by_policy | foreign_link
# RestoreResult.counters  — числа для FR-7.5

class StreamRestorer:
    def feed(self, chunk: str) -> str     # весь текст, который уже можно показать (не прирост)
    def finish(self) -> RestoreResult     # полное восстановление всего ответа
```

Порядок работы:

1. **Ссылки.** В тексте находятся голые адреса (и с `www.` без схемы), `mailto:`, цели ссылок Markdown — со скобками внутри, определения ссылок Markdown — в начале строки, как в CommonMark, в том числе с целью в угловых скобках на следующей строке и с пробелами (`[1]: <https://… …>`), — и значения атрибутов (`href`, `src`, `srcset`, `action`, `formaction`, `poster`, `data`, `background`, `cite`, `ping`, `style`, `content`) — последние целиком, вместе с кавычками и переводами строк внутри, до той же кавычки. Голый адрес тянется и через кавычки; адрес сразу после кавычки кончается такой же кавычкой. Из цели ссылки выбрасываются табуляции и переводы строк, как это делает браузер, и в ней разбирается каждый адрес: хост — по правилам браузера (в имени пользователя нет `/?#\`, а `\` — то же, что `/`). Ссылка считается нашей, только если хост каждого адреса в ней целиком — выданная подмена или собран только из выданных частей (проверка ограничена числом частей самой длинной подмены): иначе наш адрес в начале атрибута прикрыл бы чужой после него (`srcset`, незакрытая кавычка, `?next=https://…`). Значение без адреса (`data="…"` в коде) ссылкой не считается и восстанавливается как обычный текст; так же — атрибут, стоящий после `(` или `,` вне любого тега HTML (именованный аргумент в коде: `requests.post(url, data="…")`), ссылки внутри него проверяются как в обычном тексте. В CSS — и в атрибуте `style`, и в элементе `<style>` — аргумент `url(…)` и `@import "…"` берутся целиком (в кавычках — до той же кавычки, без кавычек — до `)`). Хост, записанный выданной меткой адреса, узла или домена (`http://<IP_1>:8080/`), — наш. `file:///…` (без узла) и `//TODO:` в коде посторонними ссылками не считаются.

Уточнения 15.10.2026 (раунды исправлений по ревью восстановления), все — в сторону «не восстанавливать»:

- Адрес разбирается по правилам браузера (WHATWG): у `http`, `https`, `ws`, `wss`, `ftp` любая серия `/` и `\` после схемы пропускается, даже пустая (`http:evil…`); `\\узел` и `/\узел` без схемы — тоже узел; хост — после **последнего** `@`, а имя пользователя тянется и через пробелы (`https://наш x@evil…` ведёт на evil).
- Цель ссылки проверяется в четырёх прочтениях ссылок на знаки — как написано, как текст HTML, как значение атрибута и как цель CommonMark; наша она, только если наша в каждом (`href="&#47;&#47;evil…"`, `evil&#46;org`, `&nbsp` без `;`). Значения атрибутов без кавычек и определения ссылок Markdown без угловых скобок — тоже цели.
- CSS: кроме `url()` и `@import` — `image-set()`, `-webkit-image-set()`, `src()`; имена этих функций узнаются и записанными экранированиями (`u\72l(`, `@\69mport`), а ссылка CSS с `\` в имени или адресе нашей не бывает: браузер раскрывает экранирования до загрузки. Незакрытая строка CSS тянется до конца ответа; между `@import` и строкой допускаются комментарии.
- Значение `srcdoc` (вложенная страница, ссылки на знаки раскрываются дважды) нашим не бывает; если в ответе есть тег `<base>`, адреса без узла — посторонние.
- Потоковый показ останавливается перед незакрытой ссылкой (раздел 7, потоковый режим). `mailto:` — наш, только если адрес целиком выданная замена и параметров нет. Внутри остальных ссылок ничего не восстанавливается, а ссылка помечается `foreign_link` (FR-7.8).
2. **Точный проход.** Замены ищутся по виду записи (`surrogates.Finder`): метки, IPv4 и IPv6, MAC, SID, имена через точку — и сверяются с таблицей чата словарём, поэтому время не зависит от размера таблицы. В имени через точку берутся самые длинные цепочки частей, которые есть в таблице. Границы: у адреса — не цифра и не точка с цифрой, у имени — не буква, не цифра, не дефис. Подстановка не использует строку-шаблон, поэтому обратные косые черты в оригиналах (пути Windows) не искажаются.
3. **Проход по искажённым меткам.** Строгий шаблон: необязательный открывающий ограничитель в видах `<`, `\<`, `&lt;`, `[[`; тип без учёта регистра; `_` или `\_`; номер; необязательный закрывающий ограничитель. Между частями допускаются пробелы. После номера не должна идти цифра. Номер и тип берутся как написаны; нечёткое сравнение не применяется (FR-7.3). Такие замены помечаются `altered`.
4. **Составные подмены.**
   - Имена: строки вида доменного имени разбираются по частям; известные псевдонимы частей и `domain-N.example` заменяются по таблицам, неизвестные части остаются. Имя, собранное из частей, которого не было в запросе, помечается `derived`.
   - IPv4: адрес, которого нет в таблице, но чей префикс `/24` совпадает с префиксом выданной частной подмены, преобразуется обратной перестановкой и помечается `derived` (FR-7.6).
   - MAC: любой MAC-адрес в ответе приводится к 12 цифрам и ищется в таблице, поэтому смена разделителей не мешает.
5. **Неизвестные метки.** Строки, совпадающие с видом метки, но отсутствующие в таблице, помечаются `unknown` (FR-7.4).
6. **Политика.** Сущности с политикой «скрывать без восстановления» не заменяются и помечаются `kept_by_policy` (FR-7.7).

Потоковый режим: ни одна замена не содержит пробелов, поэтому `feed` восстанавливает и отдаёт текст до последнего пробельного символа, удерживая незавершённый хвост. Если хвост без пробелов длиннее 512 знаков, отдаётся его начало до последнего знака, который не входит ни в одну запись замены (буквы, цифры и `_.:-/<>[]&;\` — входят). `feed` возвращает весь показываемый текст, а не прирост: восстановление более длинного префикса может изменить начало (ссылка, закрытая позже). Пока ответ идёт, показанный текст предварительный и копировать его нельзя; по окончании потока `finish` выполняет полное восстановление всего ответа, и страница показывает его — правила ссылок (FR-7.8) действуют на нём.

Регрессионные тесты закрепляют отказы, найденные исследованием в других инструментах:

- метка с квадратными скобками не воспринимается как класс символов;
- `PERSON_1` не портит `PERSON_10`;
- оригинал с `\U` не вызывает ошибку;
- две разные метки никогда не восстанавливаются одним значением;
- оригинал не подставляется внутрь посторонних слов.

## 8. Проверка утечек (`leakcheck.py`)

```python
def check(text: str, chat: ChatState, settings: Settings) -> list[Leak]
```

1. Из текста вырезаются все замены чата (в том числе записанные в другом виде) и все открытые значения — правила «открыть» и список «никогда не скрывать»; открытые значения — только целыми словами (граница — буквы), так что открытое «Ivan» не прячет от проверки «ivanov». Случайное совпадение подмены с настоящим значением и части значения, открытого намеренно, утечкой не считаются.
2. В остатке ищутся все написания сущностей чата (кроме значений, с которых пользователь снял замену) и все значения списка «всегда скрывать» — по тем же правилам границ, что и в слое словарей (раздел 5.4). Одинаковые правила нужны, чтобы проверка не блокировала текст из-за совпадения внутри постороннего слова.
3. Любая находка возвращается с указанием сущности и места.

Проверка вызывается дважды: в `pipeline` перед выдачей очищенного текста и в `egress.cloud` перед отправкой (SEC-2). Она ловит ошибки сборки запроса; значение, которое не нашёл ни один слой, ей неизвестно.

## 9. Документы (`ingest`)

- **Docling** (MIT) преобразует DOCX, XLSX, PPTX, PDF, HTML, CSV, EML, MSG и изображения в Markdown. Обращение к внешним сервисам в Docling выключено; модели загружены заранее командой `cleaner models download`.
- **Распознавание текста**: служба `ocr-ru` самого сервера (PaddleOCR-VL), маршрут шлюза `/pages/ocr`. Cleaner разбивает скан на страницы-изображения и отправляет их по одной; ответ — Markdown страницы. Элемент, полученный распознаванием, получает отметку в `meta` (FR-2.5). Что нужно учитывать:
  - пределы службы — 20 МБ и 12 000 точек по стороне на страницу, очередь на две задачи (дальше ответ 503 с `Retry-After`, Cleaner ждёт и повторяет);
  - скорость — 72 секунды на страницу на процессоре, поэтому многостраничный скан идёт фоновым заданием с индикатором хода;
  - изображения страниц до суток лежат во временных файлах службы распознавания, вне зашифрованной базы Cleaner.
- **Текстовые файлы** читаются напрямую. Кодировка: метка порядка байтов, UTF-16 без метки (по повторяющимся старшим байтам), строгий UTF-8; доля кириллицы решает только между Windows-1251 и CP866 — однобайтовые кодировки декодируют любой файл (FR-2.4). CSV тоже читается как текстовый файл, а не через Docling: выгрузки Excel бывают в Windows-1251, а Docling ждёт UTF-8.
- Изображения PNG и JPEG идут прямо в `ocr-ru`, минуя Docling. Скан в PDF определяется постранично: страница без слоя текста (меньше 20 знаков) и с изображением распознаётся `ocr-ru`, остальные разбирает Docling без собственного распознавания. Клиент `ocr-ru` живёт в `local_llm.py` (сетевой код разрешён только там, SEC-1); `ingest` получает распознавание вызываемым объектом и сам сети не касается. Адрес распознавания выводится из адреса модели: `<адрес без /v1>/pages/ocr`.
- Загруженный файл Cleaner на диск не пишет: байты держатся в памяти до конца задания (FR-2.7). Временные файлы бывают только у библиотек — Starlette сбрасывает часть формы больше 1 МБ во временный файл на время запроса, Docling распаковывает XLSX и PPTX во временный каталог; на сервере это личный `/tmp` службы (`PrivateTmp=yes`). Имя файла используется только для расширения и нигде не хранится. Извлечённый Markdown становится оригиналом элемента чата.
- До Docling каталог ZIP файлов DOCX, XLSX и PPTX читается без распаковки, и файл отклоняется с причиной, если распакованное больше 512 МБ (ZIP-бомба), XML больше 32 МБ, область листов XLSX больше 1 000 000 ячеек или текст таблицы по числу заполненных ячеек заведомо длиннее `max_text_chars`: Docling создаёт объект на каждую ячейку области, и таблица на 180 000 строк поднимала службу до 5 ГБ (раздел 15). Файл считается PDF по сигнатуре в начале, а не по упоминанию `%PDF-` в тексте.
- Ошибка извлечения даёт элемент со статусом `failed` и причиной (FR-2.9).

## 10. Облачный шлюз (`egress`)

### 10.1. Сборка запроса

`pipeline.build_outgoing(state, turns, settings, provider_id, model) -> Outgoing` собирает исходящий текст заново при каждой отправке (ходы — из элементов чата, их выбирает служба):

- входные элементы — очисткой оригиналов с текущими правилами чата и сохранёнными находками слоёв 4–5 (модели не вызываются);
- ответы облака и вставленные вручную — их записанный текст, в котором заменены известные значения чата, словарь и правила (FR-8.11): ищут только известное, новых сущностей ответ модели не создаёт;
- системная часть — служебная инструкция и очищенные инструкции пользователя (элементы `instruction`);
- соседние ходы одной роли склеиваются через пустую строку (Anthropic требует чередования), ответы до первого вопроса не входят, последним в диалоге должен быть вопрос;
- не входят: тексты, обработка которых не удалась (`failed`), и ответы локальной модели — она видела оригиналы, и её ответ их содержит. Текст в очереди или в работе отправку запрещает.

```python
class OutgoingContext:      # неизменяемый; создаётся только в pipeline (тест состава программы, SEC-1)
    chat_id: str
    provider_id: str
    model: str
    system: str
    messages: tuple[OutMessage, ...]   # role: user | assistant, text
    def digest(self) -> str            # sha256 содержимого: экран подтверждения показывает его, отправка сверяет
```

`Outgoing` несёт ещё найденные проверкой утечек оригиналы (по итоговым текстам, с номером сообщения) и число фрагментов запрещённых типов; отправка возможна, только если их нет. Экран подтверждения (FR-8.4) показывает ровно этот объект; отправка пересобирает его и уходит, только если отпечаток совпал с показанным. Проверка подключения (FR-8.2) получает `OutgoingContext` из `pipeline.probe_context` — постоянный текст без данных пользователя.

### 10.2. Служебная инструкция

> В тексте встречаются обозначения вида `<PERSON_1>`, `<EMAIL_2>`, а также условные адреса и имена узлов. Это непрозрачные идентификаторы, заменяющие скрытые данные. Переписывай их посимвольно: не переводи, не склоняй, не изменяй и не придумывай новых.

Инструкция передаётся на русском и английском. Её действие не измерено; восстановление не полагается на то, что модель её соблюдает.

### 10.3. Отправка

`egress.cloud.send(ctx, connection, state, settings, *, cancel, outcome) -> Iterator[str]` — обычный генератор: отправка идёт фоновым заданием в потоке, как остальные долгие операции службы.

1. принимает только `OutgoingContext` (иначе `TypeError`) и вызывает `leakcheck.check` по всем его текстам; при находке — `LeakDetected`, запрос не отправляется;
2. проверяет адрес подключения и дополнительные поля;
3. передаёт запрос адаптеру протокола и отдаёт фрагменты ответа по мере получения; `cancel` прекращает чтение, `outcome` получает признак обрезки по пределу длины.

Подключение (`Connection`) служба собирает из записи `providers`: протокол, адрес, способ передачи ключа, ключ, предел длины ответа, дополнительные поля; в его строковом виде ключа нет.

Два адаптера:

- **`openai`** — `POST {base_url}/chat/completions`, `stream: true`, события `data: {…}` с `choices[0].delta.content`, конец — `data: [DONE]`; рассуждения (`reasoning_content`) не показываются;
- **`anthropic`** — `POST {base_url}/v1/messages`, заголовок `anthropic-version: 2023-06-01`, обязательный `max_tokens`, события `content_block_delta` с `text_delta`, конец — `message_stop`; блоки рассуждений (`thinking_delta`) не показываются.

Для каждого подключения задаётся способ передачи ключа: заголовок `x-api-key` или `Authorization: Bearer`. Совместимые провайдеры расходятся в этом (раздел 19). Содержимое `extra_body` подключения добавляется в тело запроса (например, требование нулевого хранения у маршрутизаторов); поля, которыми можно заменить сам запрос или добавить инструменты, файлы и поиск провайдера (`model`, `messages`, `system`, `stream`, `tools`, `tool_choice`, `functions`, `function_call`, `attachments`, `files`, `web_search_options`, `mcp_servers`, `container`), отклоняются при сохранении и при отправке.

Названия моделей задаёт администратор; в коде они не зашиты.

Ограничения (FR-8.8, SEC-13):

- только текстовые сообщения;
- HTTPS для любого адреса, кроме петлевого;
- проверка сертификатов включена, переадресации не выполняются, переменные прокси окружения не читаются;
- автоматических повторов нет;
- тело запроса и ключ в логи не попадают.

Ошибка провайдера (`ProviderError`) в строковом виде — постоянное объяснение с кодом ответа и видом ошибки провайдера: его хранит `meta` ответа и видит пользователь (FR-8.9). Сообщение самого провайдера может повторять текст запроса, поэтому оно не пишется ни в `meta` (открытый столбец), ни в журнал, а показывается только на экране проверки подключения, где данных пользователя нет; ключ в нём заменяется на `***`.

Клиент — `httpx`.

### 10.4. Ответ в чате

Отправка записывает элемент-ответ (`source = 'api'`, `status = 'running'`, подключение и модель в `meta`) той же транзакцией, что и состояние чата, и ставит задание в собственный пул отправок из четырёх потоков: общий пул из двух потоков сканы занимают на десятки минут. Фрагменты ответа копятся в памяти (`LiveAnswers`); страница получает их событиями сервера (`GET …/items/{id}/stream`: весь восстановленный к этому моменту текст, затем `done`). Поток событий только читает: уход со страницы генерацию не прерывает. «Остановить» (`POST …/stop`) прекращает чтение. По окончании ответ записывается: `done`; `partial` с полученной частью и причиной — при остановке, обрезке по пределу длины или ошибке провайдера посреди потока; `failed` — если не пришло ничего. Остановка службы прерывает идущие ответы и сохраняет их неполными. В журнал — `cloud_send` (подключение, модель, число сообщений и знаков) и счётчики восстановления.

Вопрос локальной модели вместо облачной (FR-9.4) — кнопка в чате: модель получает оригиналы входных текстов, инструкции — системной частью, ответы облака — восстановленными; задание идёт в общем пуле. Её ответ (`source = 'local'`) показывается как получен: в нём нет замен, а «восстановление» приняло бы настоящий адрес из выданной подсети за выведенный.

## 11. Локальная LLM (`local_llm.py`)

- Клиент OpenAI-совместимого адреса (`/v1/chat/completions`). На `example` это шлюз LiteLLM по петлевому адресу, порт 30000, модель по умолчанию `qwen-27b-fast` (проверка E, раздел 19: `qwen-27b` рассуждает и не укладывается в предел ответа); ключ клиента шлюза выпускается командой `sudo ai-ctl gateway-key create cleaner` и хранится в файле окружения службы.
- При сохранении настройки адрес проверяется: петлевой, из частных диапазонов или из списка доверенных; иначе настройка отклоняется (FR-9.1, SEC-12).
- Ограничение ответа схемой JSON задаётся параметром `response_format`. Доходит ли он через шлюз до vLLM и соблюдает ли модель схему, проверяется в начале этапа 4.
- Три применения: слой 5 (раздел 5.6), проверка остаточного риска (модель получает очищенный текст и возвращает догадки об организации, людях и месте), ответ на вопрос вместо облачной модели (FR-9.4).
- Проверка остаточного риска запускается кнопкой на экране проверки, а не после каждой очистки; её результат хранится зашифрованным (`items.risk_enc`).
- Тот же модуль — клиент `ocr-ru` (раздел 9). Ключ шлюза — переменная `CLEANER_GATEWAY_KEY` в файле окружения службы; в базе и в файлах репозитория его нет. Клиент не читает переменные прокси окружения.

## 12. Шифрование (`storage/crypto.py`)

- Алгоритм — AES-256-GCM из библиотеки `cryptography`. Каждое значение шифруется со случайным 96-битным одноразовым числом; в проверяемые данные входят имя таблицы, столбца и идентификатор строки, чтобы зашифрованное значение нельзя было переставить в другое место.
- **Главный ключ** — 32 случайных байта. Лежит в `/etc/cleaner/cleaner.env` с правами `0600 root:root` и попадает к службе переменной окружения через `EnvironmentFile=`: файл читает systemd до сброса привилегий, сама служба открыть его не может. Так же хранятся ключи остальных служб сервера.
- **Ключ чата** — 32 случайных байта, хранится в `chats.dek_wrapped` зашифрованным главным ключом; им шифруются название, состояние и элементы чата. Ключ перестановки адресов (раздел 6.2) — отдельные 32 случайных байта внутри зашифрованного состояния чата: стойкость та же, а состояние самодостаточно.
- **Общий ключ** — для словаря организации, ключей подключений и эталонных примеров; хранится так же в `settings`.
- Удаление чата стирает его ключ; с `secure_delete` остатки строк в файле перезаписываются, а сразу после удаления выполняется контрольная точка WAL с усечением журнала — иначе образы страниц с обёрнутым ключом чата остались бы в файле `-wal` до следующей автоматической контрольной точки (FR-1.4).
- `cleaner key export` записывает главный ключ в файл, зашифрованный паролем (scrypt и AES-GCM); `cleaner key import` восстанавливает его на другой машине (FR-12.3). Обе команды выполняются от root.

Ключ в окружении процесса виден root и самому процессу. Это тот же предел, что в SEC-6: шифрование защищает от кражи файла базы или копии, а не от администратора сервера.

## 13. Вход и сессии (`web/auth.py`)

- Пароли — Argon2id (`argon2-cffi`).
- Сессия — случайный 256-битный токен в cookie с признаками `HttpOnly`, `SameSite=Strict` и `Secure` (при TLS). В базе хранится хэш токена. Сессия истекает через 8 часов бездействия.
- Хэш пароля при входе считается в пуле потоков, а не в цикле событий: иначе каждая попытка входа останавливала бы остальные запросы. Одновременно — не больше четырёх проверок (около 64 МиБ каждая); запрос, прождавший слот дольше 5 с, получает 503 «попробуйте позже», и это не считается неудачной попыткой.
- Тело любого запроса, включая вход, ограничено 8 МиБ; предел считается по принятым байтам, а не по `Content-Length`. Под TLS отдаётся `Strict-Transport-Security: max-age=31536000` без `includeSubDomains`.
- При заполнении таблицы неудачных попыток входа вытесняются сначала записи меньше чем с пятью неудачами, затем одна запись без действующей паузы, затем самые старые: перебор случайных логинов не сбрасывает паузу настоящей учётной записи. Существует ли логин, здесь не учитывается — иначе по ответам можно было бы узнать, какие логины есть.
- Защита от подделки запросов: `SameSite=Strict` и в каждой форме POST — отдельный случайный токен сессии (`sessions.csrf`), не сам токен входа. Форма входа защищена своим токеном в cookie (двойная отправка).
- После пяти неудачных попыток входа для логина вводится нарастающая задержка; попытки пишутся в журнал.
- Каждый запрос к чату проверяет, что чат принадлежит вошедшему пользователю (FR-1.5).

## 14. Веб-интерфейс (`web`)

### Экраны

| Экран | Содержание |
|---|---|
| Вход | Логин и пароль |
| Чат | Слева список чатов с поиском. В центре — лента элементов. Внизу — поле ввода с загрузкой файла, поле «Ответ модели», выбор подключения и модели |
| Проверка | Две панели «оригинал / очищенное» с подсветкой; сводка и предупреждения; действия «Скопировать», «Отправить», «Спросить локальную модель», «Сохранить как эталон»; для администратора — «В словарь организации» (FR-6.6) |
| Таблица чата | Замена, тип, оригинал, число вхождений; действия: снять замену, сменить тип, объединить, изменить значение для восстановления |
| Настройки (администратор) | Подключения, локальная модель, политики типов, словари и импорт, шаблоны, пользователи, журнал |

Элемент-ответ показывается с переключателем «восстановлено / как получено» и счётчиком (FR-7.5, FR-7.11).

### Правка на экране проверки

Выделенный в оригинале фрагмент браузер передаёт серверу значением вместе с выбранным типом. Позиции не передаются: браузер приводит переводы строк CRLF к LF, и позиции разошлись бы с сохранённым оригиналом. Сервер проверяет, что значение есть в тексте элемента — с той же нормализацией, что при поиске (регистр, «ё/е», пробельные знаки), — и скрывает все вхождения значения в чате (FR-6.3). Каждая правка записывается правилом в состояние чата и запускает повторную очистку входных текстов чата; значение, которое теперь скрывается, но стояло открытым в прежнем варианте текста, помечается в элементе (`exposed`, FR-6.8).

### Безопасный вывод (`render.py`)

- Ответ показывается как текст с выделением восстановленных мест, без разбора Markdown: HTML и изображения из ответа не исполняются и не загружаются, ссылки — просто текст (SEC-10). Всё содержимое экранируется; готовая разметка собирается только в `render.py`.
- Заголовок политики безопасности содержимого: `default-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; form-action 'self'; base-uri 'none'` (SEC-9). Встроенных скриптов и стилей нет.
- Скрипт один — `static/app.js`: копирование, парная подсветка замен, перенос выделения в форму. Остальное — обычные формы с перенаправлением.

### Фоновые задания (`jobs.py`)

Извлечение текста, слои 4 и 5 и запросы к локальной модели выполняются в пуле из двух потоков; отправки облаку — в своём пуле из четырёх (раздел 10.4). Состояние задания (`queued`, `running`, `done`, `failed`, у ответа облака ещё `partial`) пишется в `items.status`; страница опрашивает его раз в секунду. «Повторить» ставит текст в очередь одним условным `UPDATE`: двойное нажатие не запускает модели дважды. При остановке службы пулы не берут новых заданий, отменяют ждущие и ждут идущие не дольше 30 с; недождавшиеся — и при следующем старте всё, что осталось в `queued` или `running`, — получают `failed` с причиной «прервано» и кнопкой повтора (NFR-6). Прерванная проверка остаточного риска получает своё состояние `interrupted`, а её догадки стираются, когда меняется очищенный текст. Служба работает одним процессом.

Потоковый ответ облачной модели передаётся браузеру событиями сервера (раздел 10.4).

Всё остальное (подключения, локальная модель, политики, словари) хранится в базе и настраивается в интерфейсе.

Команды (`python -m cleaner …`):

| Команда | Действие |
|---|---|
| `init --admin <логин> --env-file <путь>` | Создать базу, главный ключ (строкой `CLEANER_MASTER_KEY=…` в новый файл с правами 0600), первого администратора (FR-12.2) |
| `serve` | Запустить службу |
| `user add / disable / passwd` | Учётные записи |

| `models download` / `models verify` | Загрузить модели в `models_dir` (единственная команда, которой нужен интернет): запись в `<каталог>.incoming`, манифест sha256 каждого файла, перенос готового каталога — как веса сервера в vLLM; `verify` сверяет файлы с манифестом |
| `verify` | Самопроверка на подложенных значениях (FR-12.4) |
| `eval` | Измерение качества на эталонном наборе (FR-12.5) |

Главный ключ и ключ шлюза в этот файл не входят: они приходят из окружения службы (раздел 12). Логи приложения пишутся в журнал systemd; журнал доступа uvicorn выключен — в строке запроса бывает поиск по названиям чатов (SEC-11).

Зависимости закрепляются файлом с версиями и контрольными суммами (SEC-14). Файл для сервера собирается под Linux и Python 3.12 отдельно от файла машины разработки (Windows, Python 3.14): набор транзитивных зависимостей у платформ разный. Файлы `requirements-linux.txt` и `requirements-dev-linux.txt` собирает на машине разработки `deploy/lock_linux.py`: pip из `.venv` разрешает зависимости для Linux x86_64 / CPython 3.12 (только колёса), набор пересчитывается по маркерам сервера, версии и контрольные суммы берутся из файлов машины разработки — на сервере те же версии. На сервере окружение создаётся `python3.12 -m venv` и `pip install --require-hashes --only-binary=:all:`; пакеты качает установщик от root, как у остальных служб сервера.

### Размещение на `example`

Сервер описан в соседнем репозитории `D:\vsc\vLLM`; его правила действуют и для Cleaner.

**Служба.** Юнит `cleaner.service`, код и окружение — в `/opt/cleaner`, данные — в `/var/lib/cleaner` (`0700`, владелец `cleaner`). Не в `/opt/ai`: этот каталог закрыт для чужих учётных записей (`drwxr-x--- aiservice`, `dashboard/README.md` в vLLM), и `cleaner` не смог бы в него войти; по той же причине панель управления сервера живёт в `/opt/ai-dashboard`. Добавить `cleaner` в группу `aiservice` нельзя — это отменило бы смысл отдельной учётной записи.

```ini
[Service]
User=cleaner
Group=cleaner
WorkingDirectory=/opt/cleaner
EnvironmentFile=/etc/cleaner/cleaner.env
Environment="CLEANER_CONFIG=/etc/cleaner/cleaner.toml"
Environment="HOME=/var/lib/cleaner"
Environment="HF_HUB_OFFLINE=1"
Environment="TRANSFORMERS_OFFLINE=1"
Environment="HF_HUB_DISABLE_TELEMETRY=1"
Environment="DO_NOT_TRACK=1"
Environment="TOKENIZERS_PARALLELISM=false"
# Без таблицы nftables cleaner_egress выход наружу не ограничен — тогда служба не стартует.
ExecStartPre=+/usr/local/sbin/cleaner-egress.sh check
ExecStart=/opt/cleaner/.venv/bin/python -m cleaner serve
MemoryMax=8G
Nice=10
CPUWeight=20
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
NoNewPrivileges=yes
RestrictSUIDSGID=yes
ReadWritePaths=/var/lib/cleaner
Restart=always
RestartSec=20
# Этап 3: IPAddressDeny=/IPAddressAllow= (до него — как у остальных служб сервера) убраны,
# выход наружу ограничивает таблица nftables cleaner_egress.
```

- Учётная запись отдельная, не `aiservice`: цепочка наблюдения сервера записывает исходящие попытки `aiservice` как происшествия, и законные запросы Cleaner к провайдерам засоряли бы её журнал.
- Приоритет процессора ниже, чем у распознавания речи, — как у эмбеддингов.
- Предел памяти 8 ГБ — по замеру 14.10.2026 (план 2+4): пик службы 5,0 ГБ — модели слоя 4 в памяти (около 2,4 ГБ), PDF на 50 страниц, 100 000 знаков со слоем 4 и таблица XLSX на 180 000 строк (5 МБ) в Docling; × 1,5 с округлением вверх. Больше в Docling не попадает: таблица, текст которой заведомо длиннее `max_text_chars` (по числу ячеек), область листов больше 1 000 000 ячеек, больше 32 МБ XML в DOCX/PPTX/XLSX или больше 512 МБ распакованного вообще отклоняются до Docling (раздел 9; замер — примерно 2,8 КБ памяти на заполненную ячейку).
- `models_dir` и `max_file_mb` в `/etc/cleaner/cleaner.toml` установки этапа 1 дописаны руками при обновлении 14.10.2026: установщик кладёт файл настроек только при первой установке.
- `HOME` указан явно и лежит внутри `ReadWritePaths`: при `ProtectSystem=strict` библиотека, пишущая в домашний каталог, иначе получает отказ.

**Вход.** Порт открывается в `ufw` только для `example/19` (`ufw allow proto tcp from example/19 to any port 5464`, как у остальных установщиков сервера). Служба слушает адрес `example`, а не `0.0.0.0`: из других сетей она недоступна, даже если правило экрана окажется шире задуманного. Сертификат самоподписанный, собственный — в `/etc/cleaner/tls/` (RSA-4096, 10 лет, SAN `IP:example, DNS:example`), а не общий сертификат сервера: ключ общего читает только группа `aidash`, его SAN не покрывает `example`, а Cleaner с этапа 3 — единственная служба с выходом наружу, и её взлом не должен отдавать ключ остальных TLS-портов. Отпечаток печатают установщик и `check-cleaner.sh`; в документы он не выписывается — по правилу vLLM «отпечаток читается командой».

**Файлы установки** (`deploy/`): `cleaner.service` (к тексту выше добавлены `After=`/`Wants=network-online.target cleaner-egress.service` и `WantedBy=multi-user.target`), `cleaner-egress.sh` и `cleaner-egress.service` — выход наружу (этап 3), `cleaner.toml` — шаблон настроек сервера, ставится один раз, `install-cleaner.sh` — установка и обновление с откатом, `check-cleaner.sh`, `lock_linux.py`. На сервер едет только закоммиченное дерево.

**Выход наружу (этап 3).** Директивы `IPAddressDeny` и `IPAddressAllow` из юнита убраны, а границы задаёт `deploy/cleaner-egress.sh` — своя таблица nftables `inet cleaner_egress` (запасной вариант этого раздела вместо цепочки `iptables` по образцу `ai-egress-guard.sh`, ревью этапа 3):

```
table inet cleaner_egress, цепочка output (hook output, priority filter), пакеты учётной записи cleaner:
  к внутренним сетям сервера          → пропустить
  TCP 443 по IPv4                     → записать новое соединение («cleaner-out: », не чаще 30 в минуту) и пропустить
  остальное, IPv6 кроме петли тоже    → записать в журнал («cleaner-egress: », не чаще 6 в минуту) и отклонить
```

- Запись разрешённых соединений на 443 показывает, к каким адресам служба ходила, — без содержимого.
- Запросы DNS идут локальному резолверу по петле и под ограничение не попадают.
- В той же таблице цепочка `input` отбрасывает соединения с портом 5464 отовсюду, кроме `example/19` и петли: второй слой за правилом `ufw`, который раньше давал `IPAddressDeny=` юнита (он ограничивал оба направления и снят ради выхода на 443).
- Почему своя таблица, а не цепочка `iptables`: `ufw` работает через `iptables-nft` в таблицах `ip filter` / `ip6 filter` и при `reload` и `disable` чистит их целиком — вход в цепочку пропадал бы молча (в том числе после срабатывания `ufw-failsafe` и ручного `ufw --force enable`), и выход службы становился бы **шире**. Чужую таблицу `ufw` не видит. Отказ в своей таблице окончателен, что бы ни решили цепочки `ufw`: пакет проходит, только если его пропустили все таблицы. Таблица заменяется одной транзакцией `nft -f` — пустой она не бывает ни мгновения.
- Правила nftables не переживают перезагрузку: таблицу ставит юнит `cleaner-egress.service` при загрузке. Без таблицы служба не стартует (`ExecStartPre=+/usr/local/sbin/cleaner-egress.sh check`: таблица на месте, в ней отбор по учётной записи и отказ); `Requires=` не годится — перезапуск таблицы перезапускал бы и службу. Установщики vLLM с `ufw reload` правок не требуют.
- Список внутренних сетей таблицы — ещё одна копия `INTERNAL_NETS` из `ai-egress-guard.sh`. Правило vLLM требует менять все копии вместе, а его тест видит только файлы своего репозитория, поэтому сверку списков делает `check-cleaner.sh`.
- Свести исключение к адресам провайдеров нельзя: они плавающие. Сузить его до имён узлов можно только через прокси со списком разрешённых имён — это записано в `IDEAS.md`, в объём не входит.

**Проверка фактом** (`deploy/check-cleaner.sh`, по образцу `check-egress.sh`): проба запускается в контрольной группе службы от учётной записи `cleaner` (`setpriv`: таблица выбирает пакеты по учётной записи, проба от root прошла бы мимо неё) и обязана показать, что шлюз сервера достижим, внешний адрес по порту 443 достижим и записан в журнал ядра (`cleaner-out:`), внешний адрес по порту 80 отклонён и записан (`cleaner-egress:`); таблица на месте (`cleaner-egress.sh check`), IPv6 отклоняется, список внутренних сетей совпадает с `ai-egress-guard.sh`. На этапе 1 положительный контроль — свой порт службы и шлюз `127.0.0.1:30000`, внешние `1.1.1.1:443` и `:80` недоступны; появление попытки в журнале ядра проверяется с этапа 3 (цепочка `AI-EGRESS-LOG` сервера следит только за `aiservice`). В список служб по умолчанию `check-egress.sh` сервера `cleaner.service` не вписывается: его раздел 1 требует `example/24` в разрешённых у всех служб, кроме «только для шлюза».

**Правки в репозитории vLLM.** Все списки vLLM — служб, источников правил экрана, хранилищ — закрыты в коде: установка Cleaner не сделает красным ни один тест или проверку, но сервер молча перестанет соответствовать собственному описанию. Cleaner — первая служба `example`, чей установщик лежит вне репозитория vLLM; код, юнит, установщик и проверки остаются в репозитории Cleaner, а в vLLM вносится только описание и точки стыка:

| Что | Где в vLLM |
|---|---|
| Порт 5464 (Cleaner, только `example`) | `CURRENT-STATE.md`, строка портов в «Хост и сеть» |
| Служба `cleaner.service` с пометкой, что установщик — в `D:\vsc\cleaner` | `CURRENT-STATE.md`, рукописная таблица служб |
| Правило экрана для 5464 | `CURRENT-STATE.md`, «Экран»: абзац после генерируемой таблицы — по образцу абзаца о порте 9988 |
| `"cleaner.service"` в список `UNITS` | `dashboard/deploy/collect-manifest.py`; после установки — `manifest.ps1 -UpdateBaseline` и `facts.py --write`, затем коммит эталона, `facts.json`, `CLAUDE.md` и `CURRENT-STATE.md` (эталон переснимается в любом случае, чтобы поглотить правило экрана) |
| Новое хранилище: оригиналы и таблицы замен, зашифрованы, срок — до удаления чата пользователем | `CURRENT-STATE.md`, «Карта хранилищ»: строка с явной пометкой «вне `STORAGES`» (запись в `STORAGES` ai-ctl требует правки `test_retention_map.py` и переустановки ai-ctl, а проверка-канарейка к зашифрованной базе неприменима) |

Цена учёта юнита в эталоне: изменение юнита в новой версии Cleaner делает сверку vLLM красной, пока эталон не переснят. Новый документ в `docs/superpowers` vLLM вносится в его `docs/README.md` — это проверяет тест vLLM.

**Правила сервера, которые нельзя нарушать при установке:**

- правки `ufw` — только под отложенным откатом с именем `ufw-failsafe` (`systemd-run --unit=ufw-failsafe --on-active=10m ufw --force disable`: проверка готовности `ai-ctl` ищет таймер по этому имени) и с проверкой новым SSH-подключением; после правки — `systemctl try-restart ai-egress-guard.service` (и `cleaner-egress.service` с этапа 3);
- `setup-ai-stack-final.sh` на сервере не запускать;
- новый порт — ниже 32768 и не из забронированных (31009, 31014);
- привилегированные действия над службами сервера — только через `ai-ctl`; ключ клиента шлюза выпускает `ai-ctl gateway-key create`;
- значения ключей не попадают в файлы репозитория и в вывод сессии.

## 17. Тесты

Правила проекта: `pytest` без параметров — быстрый набор до 60 секунд; всё, чему нужны модели, документы, локальная LLM или сеть, помечается `integration`; запускаемое вручную — `manual`; предел 30 секунд на тест; время только подставное (`clock.py`). Команды запуска объявляются в `CLAUDE.md` проекта.

| Набор | Что проверяет |
|---|---|
| Быстрый | Правила и контрольные суммы на действительных и недействительных номерах; секреты по контексту; разбор адресов и имён; объединение фрагментов; канонические ключи; свойства перестановки адресов (сохранение префиксов, обратимость); подмены хостов; восстановление, включая регрессии из раздела 7 и разрез потока в каждой позиции; проверка утечек; шифрование и стирание ключа чата; права доступа к чужому чату; тест импортов (SEC-1); отсутствие оригиналов в базе, логах и журнале на контрольном прогоне |
| `integration` | Модели слоя 4 на контрольных текстах; Docling и распознавание текста на контрольных файлах; локальная модель; адаптеры протоколов против сервера-заглушки; норма скорости слоёв 1–3 (NFR-4) — около секунды на тест, поэтому в полном наборе |
| `manual` | Запрос к настоящему провайдеру; замер скорости со слоем 4 для NFR-4 (`test_speed_stage2.py`, минуты на машине разработки) |

Быстрый набор обязан проходить и на Windows (разработка, Python 3.14), и на Linux (сервер, Python 3.12). Отдельный тест разбирает исходники пакета как код Python 3.12 и ловит синтаксис новее целевой версии. Сценарии `deploy/` проверяются на сервере скриптом `check-cleaner.sh`, в быстрый набор не входят.

Измерение качества (`eval`) — не тест, а отдельная команда: её результат сравнивается с порогами QA-3 и с предыдущим замером (QA-6).

Контрольные данные в репозитории — только вымышленные. Эталонный набор из настоящих текстов хранится в базе на сервере и в репозиторий не попадает.
