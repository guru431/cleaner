# Cleaner: спецификация

| | |
|---|---|
| Статус | черновик, на согласовании |
| Дата | 13.10.2026 |
| Требования | [TZ.md](../../../TZ.md) |
| Обоснование выбора | [отчёт исследования](../../../reports/Очистка%20данных%20перед%20облачными%20LLM.md) |

Документ описывает, как устроена система, удовлетворяющая ТЗ: части, их границы и интерфейсы, данные, алгоритмы замены и восстановления, порядок проверки. Номера `FR-…`, `SEC-…`, `NFR-…`, `QA-…` отсылают к ТЗ.

## 1. Основные решения

1. **Собственное приложение на Python**: FastAPI, серверные шаблоны Jinja2, HTMX и Alpine.js для интерактивности, SQLite для хранения. Работает службой systemd на сервере `example` (Ubuntu 24.04, Python 3.12); разработка и быстрые тесты — на Windows.
2. **Одно ядро очистки и восстановления** без сетевого доступа. Веб-интерфейс, командная строка и (в будущем) прокси — тонкие входы в это ядро.
3. **Единственный модуль выхода в сеть** принимает только объект, собранный ядром, и сам повторяет проверку утечек.
4. **Пять слоёв распознавания** дают фрагменты; фрагменты объединяются, а не голосуют.
5. **Замена зависит от типа**: метки для людей, организаций и учётных записей; подмены с сохранением формата для сети.
6. **Восстановление — точное**, без нечёткого сопоставления; искажения оформления меток разбираются по строгому шаблону.
7. **Шифрование по ключу на чат**; главный ключ служба получает при запуске из файла, доступного только root.
8. **Размещение на `example` с исключением из запрета исходящих** (решение владельца от 13.10.2026): Cleaner — единственная служба сервера с выходом в интернет, и только на порт 443.

Не используются: Presidio как каркас (распознаватели привязаны к одному языку, слияние фрагментов не подходит), LiteLLM (инцидент с пакетом в марте 2026 года и незакрытые ошибки восстановления), SQLCipher (шифрует файл целиком и не позволяет стереть ключ отдельного чата), реалистичные вымышленные имена вместо меток (скрывают от человека пропуски распознавания).

## 2. Архитектура

```
 Браузер ──HTTPS──▶ web ─────────────────────────────────────────────┐
                     │                                               │
                     ▼                                               ▼
                  pipeline ◀──▶ storage (SQLite, шифрование)        jobs
                     │
        ┌────────────┼──────────────┬───────────────┐
        ▼            ▼              ▼               ▼
     detect/*     entities/*     restore        leakcheck
        │
        ├── слой 4: локальные модели (CPU, без сети)
        └── слой 5: local_llm ──HTTP──▶ локальная LLM (петлевой или частный адрес)

     ingest (Docling, распознавание текста) — без сети

     egress.cloud ──HTTPS──▶ облачный провайдер
          ▲
          └── только OutgoingContext из pipeline.build_outgoing()
```

### Границы доверия

| Зона | Что видит оригиналы | Сеть |
|---|---|---|
| `core`, `ingest`, `storage` | да | нет |
| `local_llm` | да | только адрес локальной модели |
| `egress` | нет — только очищенный текст | только адреса подключений |
| `web` | да (показывает пользователю) | входящие соединения |

### Правила зависимостей

- Сетевые библиотеки (`httpx`, `requests`, `urllib.request`, `aiohttp`, `socket`) импортируются только в `cleaner/egress/` и `cleaner/local_llm.py`. Это проверяет тест, разбирающий импорты всех модулей пакета (SEC-1).
- При старте процесса выставляются `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1`, чтобы библиотеки моделей не обращались в интернет (NFR-2).
- `core` не зависит от `web`, `storage`, `egress`. Состояние чата `core` получает и возвращает объектами в памяти; чтение и запись выполняет `storage`.

## 4. Данные

SQLite, режим WAL, `PRAGMA secure_delete=ON`, `PRAGMA foreign_keys=ON`. Идентификаторы строк — UUID, создаются приложением. Столбцы с суффиксом `_enc` зашифрованы (раздел 12).

| Таблица | Столбцы | Назначение |
|---|---|---|
| `users` | `id`, `login`, `password_hash`, `role`, `disabled`, `created_at` | Учётные записи |
| `sessions` | `token_hash`, `user_id`, `created_at`, `last_seen_at` | Сессии входа |
| `chats` | `id`, `user_id`, `title_enc`, `dek_wrapped`, `state_enc`, `version`, `label_style`, `layers` (JSON: какие слои отключены), `provider_id`, `model`, `system_enc`, `created_at`, `updated_at` | Чат, его ключ и состояние замен |
| `items` | `id`, `chat_id`, `seq`, `kind` (`input` / `answer`), `source` (`paste` / `file` / `api` / `pasted_answer` / `local`), `original_enc`, `sanitized_enc`, `spans` (JSON: позиции, id сущности, источники — без значений), `notices` (JSON), `exposed` (JSON: id сущностей, открытых в выданном тексте, FR-6.8), `status`, `meta` (JSON: имя вида файла, признак OCR, модель, расход токенов), `created_at` | Элементы чата. Для ответа `original_enc` — текст, как он пришёл от модели |
| `dictionary` | `id`, `list` (`always` / `never`), `type`, `value_enc`, `aliases_enc`, `comment_enc` | Словарь организации |
| `patterns` | `id`, `name`, `regex`, `type`, `enabled` | Пользовательские шаблоны |
| `policies` | `type`, `policy` | Политики типов |
| `providers` | `id`, `name`, `protocol`, `base_url`, `auth_style`, `api_key_enc`, `models`, `max_tokens`, `extra_body`, `enabled` | Подключения |
| `settings` | `key`, `value` | Адрес и модель локальной LLM, вид метки по умолчанию, обёрнутый общий ключ |
| `gold` | `id`, `text_enc`, `spans_enc`, `created_at` | Эталонные примеры |
| `audit` | `id`, `ts`, `user_id`, `chat_id`, `event`, `details` (JSON без оригиналов) | Журнал |

Удаление чата удаляет его строки каскадом, включая `dek_wrapped` (FR-1.4). Исходные файлы не сохраняются (FR-2.7).

**Состояние замен чата хранится целиком** — объект `ChatState` ядра, сериализованный в JSON и зашифрованный ключом чата (`chats.state_enc`): сущности с написаниями и значениями для восстановления, таблица замен с оригиналами подмен, выданные номера (`issued`), счётчики, подсети IPv6, псевдонимы объединений, правила пользователя, посторонние метки. Отдельных таблиц для них нет:

- потеря любого из этих полей (например, `issued` или счётчиков) привела бы к выдаче других замен для уже известных сущностей — целиком состояние не расходится само с собой;
- новое поле ядра сохраняется без миграции схемы;
- обновление атомарно: запрос загружает состояние, ядро меняет его в памяти, и только после успешной очистки состояние и новый элемент записываются одной транзакцией; исключение отбрасывает изменённый объект целиком;
- одновременная запись двух запросов в один чат отсекается полем `version` (оптимистическая блокировка): второй получает отказ и повторяет очистку на свежем состоянии.

Таблица сущностей на экране чата строится из этого объекта после расшифровки.

## 5. Конвейер очистки

### 5.1. Типы

```python
class Span:            # фрагмент оригинала
    start: int         # позиции в кодовых точках Unicode
    end: int
    type: EntityType
    source: str        # rules | secrets | infra | dict | ner | llm | manual
    score: float       # 1.0 у детерминированных слоёв
    validated: bool    # подтверждён контрольной суммой или строгим форматом

class Detector(Protocol):
    name: str
    def detect(self, text: str, ctx: DetectContext) -> list[Span]: ...

class SanitizeResult:
    sanitized: str
    spans: list[ResolvedSpan]      # фрагмент оригинала + сущность + выданная замена
    notices: list[Notice]          # surrogate_in_input | foreign_label
    leaks: list[Leak]              # находки проверки утечек (раздел 8)
    blocked: list[ResolvedSpan]    # фрагменты типов с политикой «блокировать»
    deliverable: bool              # нет ни утечек, ни блокировок
```

`DetectContext` несёт словарь организации, пользовательские шаблоны, известные формы сущностей чата, правила чата и политики типов.

`pipeline.sanitize(chat: ChatState, text: str, settings: Settings) -> SanitizeResult` выполняет шаги 5.2–5.10 и обновляет `ChatState` новыми сущностями и заменами. `Settings` — общие для всех чатов словарь организации, шаблоны и политики типов. Любое исключение в любом шаге прерывает очистку целиком (FR-3.7).

### 5.2. Слой 1 — правила (`rules.py`)

Каждое правило — шаблон, необязательная проверка и необязательное требование контекста.

| Тип | Шаблон | Проверка | Контекст |
|---|---|---|---|
| `EMAIL` | адрес с `@` и доменом | — | не нужен |
| `PHONE` | `+7`/`8` и 10 цифр с любыми разделителями; международная запись с `+` | число цифр | для «голых» 10–11 цифр — слова «тел», «моб», `phone` |
| `CARD` | 13–19 цифр с пробелами или дефисами | алгоритм Луна | не нужен |
| `INN` | 10 или 12 цифр | контрольные разряды | не нужен |
| `SNILS` | 11 цифр, в том числе вида `XXX-XXX-XXX YY` | контрольное число | не нужен |
| `OGRN` | 13 или 15 цифр | контрольный разряд | не нужен |
| `BANK_ACCOUNT` | 20 цифр; IBAN | ключ счёта при найденном рядом БИК; для IBAN — остаток по модулю 97 | без БИК — слова «счёт», «р/с», «к/с» |
| `KPP` | 9 цифр | — | «КПП» |
| `PASSPORT` | серия и номер, 10 цифр с пробелами | — | «паспорт», «серия», «выдан» |
| `OMS` | 16 цифр | — | «полис», «ОМС» |
| `BIRTHDATE` | дата | допустимость даты | «дата рождения», «г.р.», «д.р.», `born`, `DOB` |

Число без контрольной суммы и без контекста не помечается. Десятизначное число, случайно прошедшее проверку ИНН (примерно одно из десяти), будет скрыто: это осознанная плата за полноту.

Все проверки контрольных сумм реализованы в `validators.py` без внешних библиотек: это около сорока строк, и так на одну зависимость меньше. Алгоритмы в исследовании получены из вторичных источников, согласных между собой; каждый покрывается тестом на известных действительных и недействительных номерах.

### 5.3. Слой 2 — секреты (`secrets.py`)

Две группы правил.

**По виду значения:**

- блоки приватных ключей PEM;
- JWT;
- токены с известными префиксами — набор правил `detect-secrets`, вызываемый как библиотека на строках текста, с выключенной проверкой у провайдера (FR-3.9).

**По контексту** (значение скрывается независимо от того, насколько оно «случайно»):

- `ключ = значение` и `ключ: значение`, где имя ключа содержит `password`, `passwd`, `pwd`, `pass`, `secret`, `token`, `api_key`, `access_key`, `credential`, «пароль»;
- параметры командной строки `--password значение`, `-Password значение`, `/p:значение`;
- учётные данные в адресе: `scheme://user:password@host`;
- поля `Password=…;` и `Pwd=…;` в строках подключения;
- в свободном тексте — слово после «пароль», «пароль:», `password is`.

Скрывается только значение, имя ключа остаётся. Пароли в свободном тексте без ключевого слова этот слой не находит; их ищет слой 5.

### 5.4. Слой 3 — инфраструктура и словари (`infra.py`, `dictionary.py`)

- **IP.** Кандидаты разбираются модулем `ipaddress`; строки, которые им не разбираются, отбрасываются. Запись с длиной префикса (`10.1.2.0/24`) — один фрагмент.
- **MAC.** Шесть пар шестнадцатеричных цифр с `:` или `-`, запись Cisco с точками.
- **Доменные имена и хосты с точками.** Имя помечается, если его последняя часть — действующий домен верхнего уровня (по встроенной копии списка публичных суффиксов, библиотека `tldextract` без обращения к сети) или внутренний суффикс из списка (`local`, `lan`, `corp`, `internal`, `intra`, `home`, `localdomain`, `ad`). Не помечаются:
  - имена из списков «никогда не скрывать» и общеизвестных доменов, включая их поддомены;
  - зарезервированные имена IANA (`example.*`, `localhost`, `test`, `invalid`);
  - имена, похожие на файл или на код, — они помечаются только в сетевом контексте (после `://`, `\\`, в параметре команды) или по словарю:
    - последняя часть совпадает с расширением файла или частым словом в коде (`md`, `py`, `zip`, `name`, `id`, `run` и подобные — встроенный список);
    - в части имени смешан регистр (`System.Net`);
    - все части, кроме последней, — числа (`1.2.3.dev`);
    - сразу за именем стоит открывающая скобка (`re.search(`).
- **Хосты без точек.** Находятся по словарю, по пользовательским шаблонам и по структурным признакам: `\\HOST\ресурс`, `HOST$`, значение параметров `-ComputerName`, `-Server`, `/S`.
- **Учётные записи.** `DOMAIN\login`; имя профиля в путях `C:\Users\<имя>\`, `/home/<имя>/`; значения из словаря. Стандартные имена (`Administrator`, `Администратор`, `Guest`, `SYSTEM`, `Public`, `Default`, `root`) не помечаются.
- **SID.** `S-1-5-21-…`; общеизвестные SID не помечаются.
- **DN.** Последовательности `CN=…,OU=…,DC=…` — один фрагмент.
- **Словарь организации.** Каждое значение и его варианты из списка «всегда скрывать» ищутся без учёта регистра, «ё/е», вида пробелов между словами (двойной, неразрывный, перевод строки) и формы записи букв (NFC); варианты одной записи словаря получают одну замену. Границы зависят от типа:
  - для типов с подменой (`IP`, `MAC`, `HOST`, `DOMAIN`, `SID`) рядом не должно быть букв, цифр, `_` и `-`;
  - для остальных типов рядом не должно быть букв — так логин `ivanov` находится и в `ivanov_backup`, но не в `ivanova`.
- **Известные значения чата.** Так же ищутся все написания уже найденных сущностей чата (FR-3.4). Короткая часть имени узла становится искомым написанием, только если она встретилась отдельно или содержит цифру либо дефис: иначе слово вроде `portal` скрывалось бы во всём тексте.
- **Правила пользователя.** Значение, которое пользователь выделил и велел скрывать, ищется в любом месте текста, без оглядки на границы.
- **Пользовательские шаблоны.** Выполняются с ограничением времени на одно выражение.

Правила для хостов без точек и учётных записей — эвристики: опубликованных измерений их точности нет. Их качество видно по счётчикам QA-2.

### 5.5. Слой 4 — модели распознавания имён (`ner.py`)

- Русский текст: `redmadrobot-rnd/rubert-base-pii-ner` (Apache-2.0), скользящее окно 512 токенов с шагом 128.
- Английский и смешанный текст: `knowledgator/gliner-pii-base-v1.0` (Apache-2.0).
- Обе модели проходят по всему тексту; находки складываются. Порог уверенности низкий (0,25) — в пользу полноты.
- Используются типы `PERSON`, `ORG`, `ADDRESS`; остальные типы моделей приводятся к типам ТЗ или отбрасываются, если их надёжнее находят слои 1–3.
- Модели загружаются один раз при первом обращении и выполняются по одной, чтобы не занимать все ядра.
- Исполнение — на процессоре. Формат (ONNX или PyTorch) выбирается проверкой в начале этапа 2 по совпадению качества и скорости.

### 5.6. Слой 5 — локальная LLM (`detect/llm.py`)

1. Текст, уже очищенный слоями 1–4, делится на части по 6 000 знаков с перекрытием 500.
2. Для каждой части модели задаётся вопрос: какие строки здесь ещё выдают человека, организацию, учётные данные или инфраструктуру. Ответ ограничен схемой JSON: список объектов `{"text": дословная строка, "type": один из типов}`. Температура 0.
3. Строка принимается, только если она дословно присутствует во входной части и не содержит уже выданных замен. Позиции находит код, а не модель.
4. Обрыв ответа по лимиту длины и невалидный JSON — ошибка: часть повторяется один раз с половинным размером, затем очистка прерывается.

### 5.7. Объединение (`merge.py`)

1. Отбрасываются фрагменты типов с политикой «не искать».
2. Фрагменты сортируются по началу; пересекающиеся сливаются в один интервал.
3. Соседние части имени (фамилия, имя, отчество, инициалы), разделённые только пробелами или точкой с пробелом, сливаются в один `PERSON`. Этот шаг появляется на этапе 2 вместе с разбором имён.
4. Тип слитого фрагмента — старший по порядку: правило пользователя, `SECRET`, фрагмент с `validated`, инфраструктура и словарь, слой 4, слой 5 (FR-3.3). Уверенность на отбрасывание не влияет.
5. Удаляются фрагменты, текст которых точно совпадает со значением правила `unmask` чата или списка «никогда не скрывать» (FR-3.6). Фрагменты из правил `mask` при этом не удаляются.

### 5.8. Сопоставление с сущностями (`resolve.py`)

Для каждого фрагмента вычисляется канонический ключ; фрагмент относится к сущности чата с тем же типом и ключом либо создаёт новую.

| Тип | Канонический ключ |
|---|---|
| `EMAIL` | адрес в нижнем регистре |
| `PHONE` | только цифры; ведущая `8` российского номера заменяется на `7` |
| Номера (`INN`, `CARD` и другие) | только цифры |
| `PERSON` | раздел 5.9 |
| `ORG` | нижний регистр, без кавычек и организационно-правовой формы, русские слова в начальной форме |
| `ADDRESS` | нижний регистр, без знаков препинания, одиночные пробелы |
| `HOST` | первая часть имени в нижнем регистре |
| `DOMAIN` | имя в нижнем регистре |
| `IP` | адрес в каноническом виде |
| `MAC` | 12 шестнадцатеричных цифр |
| `ACCOUNT` | имя входа в нижнем регистре без домена |
| `SID` | идентификатор домена (три числа после `S-1-5-21`) |
| `SECRET`, `DN`, `TERM` | значение как есть; для `TERM` — без учёта регистра |

Запись словаря организации с несколькими вариантами написания задаёт одну сущность: все варианты ведут к одному ключу.

### 5.9. Имена (`names.py`, этап 2)

- Слова упоминания разбираются `pymorphy3`: определяется роль (фамилия, имя, отчество) и начальная форма. Инициал — буква с точкой. Слова латиницей сравниваются без учёта регистра.
- Упоминание совместимо с сущностью, если каждая его часть согласуется с ней: начальные формы совпадают, инициал совпадает с первой буквой имени или отчества.
- Упоминание присоединяется к сущности, если совместимая сущность в чате ровно одна; иначе создаётся новая. Более полное упоминание дополняет сущность недостающими частями.
- Следствие: мужчина и женщина с одной фамилией, упомянутые только по фамилии, сольются в одну сущность. Это ошибка полезности, а не приватности; исправляется вручную (FR-6.4).
- Значение для восстановления — самое полное написание, встреченное в именительном падеже; если такого не было — самое полное написание как есть. Пользователь может его изменить.

До этапа 2 люди попадают в чат только из словаря и ручных правил и сопоставляются по перечисленным вариантам написания.

### 5.10. Построение очищенного текста

Для каждого фрагмента сохраняется строка `spans` с позицией в оригинале, сущностью и выданной заменой — по ним строится подсветка обеих панелей. Очищенный текст проходит проверку утечек (раздел 8) до выдачи пользователю.

Шаги 5.2–5.8 выполняются до трёх раз: написания сущностей, найденных в первом проходе, во втором ищутся в том же тексте. Так короткое имя узла связывается с полным, даже если оба впервые встретились в одном тексте.

Замены этого чата, встретившиеся во входном тексте, не трогаются; пользователь получает уведомление. Различить подмену адреса и настоящий адрес, совпавший с ней, по тексту нельзя — совпавший адрес считается подменой.

Повторная очистка того же оригинала при неизменных правилах даёт тот же результат. После изменения правил:

- элементы, не отправленные по API, очищаются заново;
- элементы, отправленные по API, хранят очищенный текст в том виде, в каком он ушёл;
- в обоих случаях элемент, в прежнем очищенном тексте которого было открыто значение, которое теперь скрывается, получает пометку (FR-6.8).

## 6. Замены

### 6.1. Метки (`labels.py`)

- Вид: `<ТИП_N>` или `[[ТИП_N]]` — по настройке, сохранённой в чате (FR-5.10). `N` — порядковый номер сущности данного типа в чате.
- Метка не содержит пробелов. Знак подчёркивания внутри не даёт Markdown принять `<PERSON_1>` за HTML-тег.
- Строки входного текста, совпадающие по виду с меткой: если такая замена есть в таблице чата — остаётся как есть (FR-5.9); если нет — выдаётся предупреждение (FR-5.8), а строка запоминается как посторонняя и при восстановлении не трогается.

### 6.2. IPv4 (`netmap.py`)

Классификация — по `ipaddress` и реестрам IANA.

| Класс | Замена |
|---|---|
| Петлевые, `0.0.0.0/8`, `255.255.255.255`, групповые, `169.254.0.0/16`, зарезервированные, документационные диапазоны, маски подсетей | не меняются |
| Частные `10/8`, `172.16/12`, `192.168/16` и `100.64/10` | перестановка с сохранением префиксов |
| Остальные (публичные) | по порядку появления: `203.0.113.1…254`, затем `198.51.100.x`, затем `192.0.2.x`; после 762 адресов — метка `<IP_N>` |

Перестановка для частных адресов:

```python
def map_private(addr: int, fixed_bits: int, key: bytes) -> int:
    out = addr & prefix_mask(fixed_bits)          # префикс диапазона не меняется
    for i in range(fixed_bits, 24):               # биты до границы /24
        prefix = addr >> (32 - i)                 # первые i бит оригинала
        flip = hmac_sha256(key, bytes([i]) + prefix.to_bytes(4, "big"))[0] & 1
        out |= (((addr >> (31 - i)) & 1) ^ flip) << (31 - i)
    return out | (addr & 0xFF)                    # последний октет сохраняется
```

`fixed_bits` равно 8, 12, 16 и 10 для четырёх диапазонов. `key` выводится из ключа чата (раздел 12), поэтому в разных чатах один адрес получает разные подмены.

Свойства, проверяемые тестами:

- два адреса с общими первыми `k` битами (`k ≤ 24`) получают подмены с общими первыми `k` битами — подсети сохраняются (FR-5.4);
- преобразование взаимно однозначно внутри диапазона и обратимо;
- диапазон и последний октет сохраняются.

Запись с длиной префикса: адрес преобразуется как обычно; если в оригинале биты после префикса были нулевыми, они обнуляются и в подмене, чтобы адрес сети остался адресом сети. Выданная строка записывается в `surrogates`.

Подмена может случайно совпасть с другим настоящим адресом чата (в диапазоне `192.168/16` это вероятно). Настоящий адрес при этом сам заменён, поэтому восстановление остаётся однозначным, а на экране проверки подмена выделена цветом. Если же совпавший настоящий адрес оставлен открытым (список «никогда не скрывать»), вместо подмены выдаётся метка `<IP_N>` (FR-5.7).

### 6.3. IPv6 (`netmap.py`)

- Не меняются: `::1`, `::`, групповые, `2001:db8::/32`.
- Локальные адреса канала (`fe80::/10`): префикс сохраняется, идентификатор интерфейса заменяется порядковым номером.
- Остальные: каждой встреченной подсети `/64` по порядку назначается `2001:db8:N::/64`; идентификатор интерфейса заменяется порядковым номером. Принадлежность одной `/64` сохраняется, отношения более коротких префиксов — нет.

### 6.4. Хосты и домены (`hostmap.py`)

Имя разбирается на регистрируемую часть (домен с публичным суффиксом; для внутренних суффиксов — две последние части) и части слева от неё.

- Регистрируемая часть — сущность `DOMAIN` — заменяется на `domain-N.example`.
- Каждая часть слева получает псевдоним из общей для чата таблицы «часть → псевдоним». Псевдоним назначается при первом появлении и больше не меняется: `host-N`, если часть впервые встретилась крайней слева или как имя без точек, и `sub-N`, если впервые встретилась в середине. Номер — общий счётчик частей.
- Части из списка служебных имён (`www`, `mail`, `smtp`, `vpn`, `ns1`, `ldap`, `_tcp` и подобные) не заменяются.
- В таблицу замен записываются и части, и составное имя целиком: так восстановление отличает имя из запроса от имени, которое модель составила сама.

Пример: `srv-dc01.msk.corp.contoso.ru` → `host-1.sub-2.sub-3.domain-1.example`; позже `SRV-DC01` → `HOST-1`, `corp.contoso.ru` → `sub-3.domain-1.example`.

- Имя без точек, написанное заглавными буквами, получает подмену заглавными.
- NetBIOS-имя домена получает подмену `DOMAIN-N`; если в словаре оно записано вариантом DNS-домена, номер у них общий.
- Номер пропускается, если строка подмены уже встречается в оригиналах чата (FR-5.7).

### 6.5. MAC и SID (`macsid.py`)

- MAC: `N`-й адрес чата → `02:00:00:xx:xx:xx` (номер в трёх последних байтах), в том же виде записи, что оригинал. `ff:ff:ff:ff:ff:ff` и нулевой адрес не меняются.
- SID: три числа идентификатора домена заменяются фиктивной тройкой, одной на домен; завершающий номер (RID) сохраняется.

### 6.6. Секреты

`SECRET` получает метку `<SECRET_N>`; значение записывается в таблицу чата (FR-4.3). При политике «скрывать без восстановления» метка в ответе не заменяется.

## 7. Восстановление (`restore.py`)

```python
def restore(chat: ChatState, answer: str, settings: Settings) -> RestoreResult   # chat не меняется
# RestoreResult.text      — восстановленный текст
# RestoreResult.segments  — разметка для выделения: restored | altered | derived |
#                           unknown | kept_by_policy | foreign_link
# RestoreResult.counters  — числа для FR-7.5

class StreamRestorer:
    def feed(self, chunk: str) -> str     # возвращает то, что уже можно показать
    def finish(self) -> RestoreResult     # полное восстановление всего ответа
```

Порядок работы:

1. **Ссылки.** В тексте находятся голые адреса, `mailto:`, цели ссылок Markdown и значения `href`/`src` — последние целиком, вместе с кавычками внутри. Ссылка считается нашей, только если её хост целиком — выданная подмена или собран только из выданных частей; `mailto:` — только если адрес целиком выданная замена и параметров нет. Внутри остальных ссылок ничего не восстанавливается, а ссылка помечается `foreign_link` (FR-7.8).
2. **Точный проход.** Замены ищутся по виду записи (`surrogates.Finder`): метки, IPv4 и IPv6, MAC, SID, имена через точку — и сверяются с таблицей чата словарём, поэтому время не зависит от размера таблицы. В имени через точку берутся самые длинные цепочки частей, которые есть в таблице. Границы: у адреса — не цифра и не точка с цифрой, у имени — не буква, не цифра, не дефис. Подстановка не использует строку-шаблон, поэтому обратные косые черты в оригиналах (пути Windows) не искажаются.
3. **Проход по искажённым меткам.** Строгий шаблон: необязательный открывающий ограничитель в видах `<`, `\<`, `&lt;`, `[[`; тип без учёта регистра; `_` или `\_`; номер; необязательный закрывающий ограничитель. Между частями допускаются пробелы. После номера не должна идти цифра. Номер и тип берутся как написаны; нечёткое сравнение не применяется (FR-7.3). Такие замены помечаются `altered`.
4. **Составные подмены.**
   - Имена: строки вида доменного имени разбираются по частям; известные псевдонимы частей и `domain-N.example` заменяются по таблицам, неизвестные части остаются. Имя, собранное из частей, которого не было в запросе, помечается `derived`.
   - IPv4: адрес, которого нет в таблице, но чей префикс `/24` совпадает с префиксом выданной частной подмены, преобразуется обратной перестановкой и помечается `derived` (FR-7.6).
   - MAC: любой MAC-адрес в ответе приводится к 12 цифрам и ищется в таблице, поэтому смена разделителей не мешает.
5. **Неизвестные метки.** Строки, совпадающие с видом метки, но отсутствующие в таблице, помечаются `unknown` (FR-7.4).
6. **Политика.** Сущности с политикой «скрывать без восстановления» не заменяются и помечаются `kept_by_policy` (FR-7.7).

Потоковый режим: ни одна замена не содержит пробелов, поэтому `feed` восстанавливает и отдаёт текст до последнего пробельного символа, удерживая незавершённый хвост. Если хвост без пробелов длиннее 512 знаков, отдаётся его начало до точки, за которой уже не может начинаться незавершённая замена. По окончании потока `finish` выполняет полное восстановление всего ответа; показанный текст заменяется итоговым.

Регрессионные тесты закрепляют отказы, найденные исследованием в других инструментах:

- метка с квадратными скобками не воспринимается как класс символов;
- `PERSON_1` не портит `PERSON_10`;
- оригинал с `\U` не вызывает ошибку;
- две разные метки никогда не восстанавливаются одним значением;
- оригинал не подставляется внутрь посторонних слов.

## 8. Проверка утечек (`leakcheck.py`)

```python
def check(text: str, chat: ChatState, settings: Settings) -> list[Leak]
```

1. Из текста вырезаются все замены чата (в том числе записанные в другом виде) и все открытые значения — правила «открыть» и список «никогда не скрывать». Случайное совпадение подмены с настоящим значением и части значения, открытого намеренно, утечкой не считаются.
2. В остатке ищутся все написания сущностей чата (кроме значений, с которых пользователь снял замену) и все значения списка «всегда скрывать» — по тем же правилам границ, что и в слое словарей (раздел 5.4). Одинаковые правила нужны, чтобы проверка не блокировала текст из-за совпадения внутри постороннего слова.
3. Любая находка возвращается с указанием сущности и места.

Проверка вызывается дважды: в `pipeline` перед выдачей очищенного текста и в `egress.cloud` перед отправкой (SEC-2). Она ловит ошибки сборки запроса; значение, которое не нашёл ни один слой, ей неизвестно.

## 9. Документы (`ingest`)

- **Docling** (MIT) преобразует DOCX, XLSX, PPTX, PDF, HTML, CSV, EML, MSG и изображения в Markdown. Обращение к внешним сервисам в Docling выключено; модели загружены заранее командой `cleaner models download`.
- **Распознавание текста**: служба `ocr-ru` самого сервера (PaddleOCR-VL), маршрут шлюза `/pages/ocr`. Cleaner разбивает скан на страницы-изображения и отправляет их по одной; ответ — Markdown страницы. Элемент, полученный распознаванием, получает отметку в `meta` (FR-2.5). Что нужно учитывать:
  - пределы службы — 20 МБ и 12 000 точек по стороне на страницу, очередь на две задачи (дальше ответ 503 с `Retry-After`, Cleaner ждёт и повторяет);
  - скорость — 72 секунды на страницу на процессоре, поэтому многостраничный скан идёт фоновым заданием с индикатором хода;
  - изображения страниц до суток лежат во временных файлах службы распознавания, вне зашифрованной базы Cleaner.
- **Текстовые файлы** читаются напрямую. Кодировка: метка порядка байтов, затем попытки UTF-8, Windows-1251, CP866; выбирается первая, декодирующая файл без ошибок и с правдоподобной долей кириллицы (FR-2.4).
- Файл обрабатывается во временном каталоге внутри каталога данных и удаляется сразу после извлечения текста (FR-2.7). Извлечённый Markdown становится оригиналом элемента чата.
- Ошибка извлечения даёт элемент со статусом `failed` и причиной (FR-2.9).

## 10. Облачный шлюз (`egress`)

### 10.1. Сборка запроса

`pipeline.build_outgoing(chat) -> OutgoingContext` собирает исходящий текст заново при каждой отправке:

- входные элементы — очисткой оригиналов с текущими правилами чата;
- ответы модели — их записанный текст, в котором дополнительно заменены известные значения чата (FR-8.11);
- системная часть — служебная инструкция и очищенная пользовательская инструкция.

```python
class OutgoingContext:      # неизменяемый
    chat_id: str
    provider_id: str
    model: str
    system: str
    messages: tuple[OutMessage, ...]   # role: user | assistant, text
```

### 10.2. Служебная инструкция

> В тексте встречаются обозначения вида `<PERSON_1>`, `<EMAIL_2>`, а также условные адреса и имена узлов. Это непрозрачные идентификаторы, заменяющие скрытые данные. Переписывай их посимвольно: не переводи, не склоняй, не изменяй и не придумывай новых.

Инструкция передаётся на русском и английском. Её действие не измерено; восстановление не полагается на то, что модель её соблюдает.

### 10.3. Отправка

`egress.cloud.send(ctx, chat_state) -> AsyncIterator[str]`:

1. вызывает `leakcheck.check` по всем текстам контекста; при находке — исключение `LeakDetected`, запрос не отправляется;
2. загружает подключение и расшифровывает ключ;
3. передаёт запрос адаптеру протокола и отдаёт фрагменты ответа по мере получения.

Два адаптера:

- **`openai`** — `POST {base_url}/chat/completions`, потоковый ответ;
- **`anthropic`** — `POST {base_url}/v1/messages`, потоковый ответ, обязательный `max_tokens`.

Для каждого подключения задаётся способ передачи ключа: заголовок `x-api-key` или `Authorization: Bearer`. Совместимые провайдеры расходятся в этом. Содержимое `extra_body` подключения добавляется в тело запроса (например, требование нулевого хранения у маршрутизаторов).

Точный вид запросов сверяется с документацией провайдеров в начале этапа 3. Названия моделей задаёт администратор; в коде они не зашиты.

Ограничения (FR-8.8, SEC-13):

- только текстовые сообщения;
- HTTPS для любого адреса, кроме петлевого;
- проверка сертификатов включена;
- автоматических повторов нет;
- тело запроса и ключ в логи не попадают.

Клиент — `httpx`.

## 11. Локальная LLM (`local_llm.py`)

- Клиент OpenAI-совместимого адреса (`/v1/chat/completions`). На `example` это шлюз LiteLLM по петлевому адресу, порт 30000, модель `qwen-27b`; ключ клиента шлюза выпускается командой `sudo ai-ctl gateway-key create cleaner` и хранится в файле окружения службы.
- При сохранении настройки адрес проверяется: петлевой, из частных диапазонов или из списка доверенных; иначе настройка отклоняется (FR-9.1, SEC-12).
- Ограничение ответа схемой JSON задаётся параметром `response_format`. Доходит ли он через шлюз до vLLM и соблюдает ли модель схему, проверяется в начале этапа 4.
- Три применения: слой 5 (раздел 5.6), проверка остаточного риска (модель получает очищенный текст и возвращает догадки об организации, людях и месте), ответ на вопрос вместо облачной модели (FR-9.4).

## 12. Шифрование (`storage/crypto.py`)

- Алгоритм — AES-256-GCM из библиотеки `cryptography`. Каждое значение шифруется со случайным 96-битным одноразовым числом; в проверяемые данные входят имя таблицы, столбца и идентификатор строки, чтобы зашифрованное значение нельзя было переставить в другое место.
- **Главный ключ** — 32 случайных байта. Лежит в `/etc/cleaner/cleaner.env` с правами `0600 root:root` и попадает к службе переменной окружения через `EnvironmentFile=`: файл читает systemd до сброса привилегий, сама служба открыть его не может. Так же хранятся ключи остальных служб сервера.
- **Ключ чата** — 32 случайных байта, хранится в `chats.dek_wrapped` зашифрованным главным ключом. Из него функцией HKDF выводятся ключ содержимого и ключ перестановки адресов (раздел 6.2).
- **Общий ключ** — для словаря организации, ключей подключений и эталонных примеров; хранится так же в `settings`.
- Удаление чата стирает его ключ; с `secure_delete` остатки строк в файле перезаписываются (FR-1.4).
- `cleaner key export` записывает главный ключ в файл, зашифрованный паролем (scrypt и AES-GCM); `cleaner key import` восстанавливает его на другой машине (FR-12.3). Обе команды выполняются от root.

Ключ в окружении процесса виден root и самому процессу. Это тот же предел, что в SEC-6: шифрование защищает от кражи файла базы или копии, а не от администратора сервера.

## 13. Вход и сессии (`web/auth.py`)

- Пароли — Argon2id (`argon2-cffi`).
- Сессия — случайный 256-битный токен в cookie с признаками `HttpOnly`, `SameSite=Strict` и `Secure` (при TLS). В базе хранится хэш токена. Сессия истекает через 8 часов бездействия.
- Защита от подделки запросов: `SameSite=Strict` и токен сессии в каждой форме и в заголовке запросов HTMX.
- После пяти неудачных попыток входа для логина вводится нарастающая задержка; попытки пишутся в журнал.
- Каждый запрос к чату проверяет, что чат принадлежит вошедшему пользователю (FR-1.5).

## 14. Веб-интерфейс (`web`)

### Экраны

| Экран | Содержание |
|---|---|
| Вход | Логин и пароль |
| Чат | Слева список чатов с поиском. В центре — лента элементов. Внизу — поле ввода с загрузкой файла, поле «Ответ модели», выбор подключения и модели |
| Проверка | Две панели «оригинал / очищенное» с подсветкой; сводка и предупреждения; действия «Скопировать», «Отправить», «Спросить локальную модель», «Сохранить как эталон»; для администратора — «В словарь организации» (FR-6.6) |
| Таблица чата | Замена, тип, оригинал, число вхождений; действия: снять замену, сменить тип, объединить, изменить значение для восстановления |
| Настройки (администратор) | Подключения, локальная модель, политики типов, словари и импорт, шаблоны, пользователи, журнал |

Элемент-ответ показывается с переключателем «восстановлено / как получено» и счётчиком (FR-7.5, FR-7.11).

### Правка на экране проверки

Оригинал отдаётся сервером как последовательность участков с атрибутами начала и конца в оригинале. При выделении браузер вычисляет границы и отправляет серверу только позиции и выбранный тип; значение сервер берёт из сохранённого оригинала сам. Позиции выделения из единиц UTF-16 пересчитываются в кодовые точки. Каждая правка записывается правилом в `chat_rules` и запускает повторную очистку неотправленных элементов чата.

### Безопасный вывод (`render.py`)

- Ответ преобразуется из Markdown с выключенным HTML и выключенными изображениями; ссылки выводятся текстом (SEC-10).
- Заголовок политики безопасности содержимого: `default-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; form-action 'self'` (SEC-9).
- HTMX и Alpine.js лежат в `static/` и отдаются самим приложением.

### Фоновые задания (`jobs.py`)

Извлечение текста, слои 4 и 5 и запросы к локальной модели выполняются в пуле из двух потоков. Состояние задания (`queued`, `running`, `done`, `failed`) пишется в `items.status`; страница опрашивает его раз в секунду. При старте службы элементы, оставшиеся в `running`, переводятся в `failed` с причиной «прервано» и кнопкой повтора (NFR-6). Служба работает одним процессом.

Потоковый ответ облачной модели передаётся браузеру событиями сервера.

## 15. Конфигурация, запуск, команды

`cleaner.toml` (путь задаётся переменной `CLEANER_CONFIG`):

```toml
[server]
host = "example"   # адрес интерфейса сети example/19
port = 5464            # ниже 32768; сверяется с таблицей портов сервера перед установкой
tls_cert = "/etc/cleaner/tls/cert.pem"    # обязателен, если host не петлевой
tls_key = "/etc/cleaner/tls/key.pem"

[paths]
data_dir = "/var/lib/cleaner"
models_dir = "/opt/ai/cleaner/models"

[limits]
max_text_chars = 500000
max_file_mb = 50
```

Всё остальное (подключения, локальная модель, политики, словари) хранится в базе и настраивается в интерфейсе.

Команды (`python -m cleaner …`):

| Команда | Действие |
|---|---|
| `init` | Создать базу, главный ключ, первого администратора (FR-12.2) |
| `serve` | Запустить службу |
| `user add / disable / passwd` | Учётные записи |
| `key export / import` | Выгрузка и загрузка главного ключа |
| `backup <путь>` | Копия базы средствами SQLite без остановки службы |
| `models download` | Загрузить модели в `models_dir` (единственная команда, которой нужен интернет) |
| `verify` | Самопроверка на подложенных значениях (FR-12.4) |
| `eval` | Измерение качества на эталонном наборе (FR-12.5) |

Главный ключ и ключ шлюза в этот файл не входят: они приходят из окружения службы (раздел 12). Логи приложения пишутся в журнал systemd.

Зависимости закрепляются файлом с версиями и контрольными суммами (SEC-14). Файл для сервера собирается под Linux и Python 3.12 отдельно от файла машины разработки (Windows, Python 3.14): набор транзитивных зависимостей у платформ разный.

### Размещение на `example`

Сервер описан в соседнем репозитории `D:\vsc\vLLM`; его правила действуют и для Cleaner.

**Служба.** Юнит `cleaner.service`, код и окружение — в `/opt/ai/cleaner`, данные — в `/var/lib/cleaner` (`0700`, владелец `cleaner`).

```ini
[Service]
User=cleaner
Group=cleaner
WorkingDirectory=/opt/ai/cleaner
EnvironmentFile=/etc/cleaner/cleaner.env
Environment="CLEANER_CONFIG=/etc/cleaner/cleaner.toml"
Environment="HOME=/var/lib/cleaner"
Environment="HF_HUB_OFFLINE=1"
Environment="TRANSFORMERS_OFFLINE=1"
Environment="HF_HUB_DISABLE_TELEMETRY=1"
Environment="DO_NOT_TRACK=1"
ExecStart=/opt/ai/cleaner/.venv/bin/python -m cleaner serve
MemoryMax=8G
Nice=10
CPUWeight=20
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
NoNewPrivileges=yes
RestrictSUIDSGID=yes
ReadWritePaths=/var/lib/cleaner
Restart=always
RestartSec=20
# До этапа 3 — как у остальных служб сервера:
IPAddressDeny=any
IPAddressAllow=localhost
IPAddressAllow=example/19
IPAddressAllow=172.16.0.0/12
```

- Учётная запись отдельная, не `aiservice`: цепочка наблюдения сервера записывает исходящие попытки `aiservice` как происшествия, и законные запросы Cleaner к провайдерам засоряли бы её журнал.
- Приоритет процессора ниже, чем у распознавания речи, — как у эмбеддингов.
- Предел памяти 8 ГБ — предварительный, уточняется замером на этапе 2 (модели распознавания имён и Docling).
- `HOME` указан явно и лежит внутри `ReadWritePaths`: при `ProtectSystem=strict` библиотека, пишущая в домашний каталог, иначе получает отказ.

**Вход.** Порт открывается в `ufw` только для `example/19`. Служба слушает адрес `example`, а не `0.0.0.0`: из других сетей она недоступна, даже если правило экрана окажется шире задуманного. Сертификат самоподписанный, с закреплением отпечатка — как у TLS-портов сервера.

**Выход наружу (этап 3).** На этапе 3 директивы `IPAddressDeny` и `IPAddressAllow` из юнита убираются, а границы задаёт `deploy/cleaner-egress.sh` — отдельная цепочка `iptables` по образцу `ai-egress-guard.sh` сервера:

```
CLEANER-EGRESS (вход: OUTPUT, пакеты учётной записи cleaner)
  к внутренним сетям сервера          → пропустить
  TCP, порт назначения 443            → пропустить
  остальное                           → записать в журнал («cleaner-egress: », не чаще 6 в минуту) и отклонить
```

- IPv6 для учётной записи `cleaner` отклоняется целиком.
- Запросы DNS идут локальному резолверу по петле и под ограничение не попадают.
- Правила `iptables` не переживают перезагрузку, а `ufw reload` убирает вход в цепочку. Поэтому цепочку ставит юнит `cleaner-egress.service` при загрузке, и его нужно перезапускать после правки `ufw` — так же, как `ai-egress-guard`. Пропажа входа делает выход **шире**, а не уже, поэтому её обязан ловить `check-cleaner.sh`.
- Свести исключение к адресам провайдеров нельзя: они плавающие. Сузить его до имён узлов можно только через прокси со списком разрешённых имён — это записано в `IDEAS.md`, в объём не входит.

**Проверка фактом** (`deploy/check-cleaner.sh`, по образцу `check-egress.sh`): проба запускается в контрольной группе службы и обязана показать, что шлюз сервера достижим, внешний адрес по порту 443 достижим (с этапа 3), внешний адрес по другому порту — нет, а попытка появилась в журнале.

**Правки в репозитории vLLM** — без них сервер перестанет соответствовать собственному описанию:

| Что | Где |
|---|---|
| Порт службы | `CURRENT-STATE.md`, «Хост и сеть» |
| Исключение из запрета исходящих и его границы | `CURRENT-STATE.md`, «Запрет исходящих» |
| Новое хранилище: оригиналы и таблицы замен, зашифрованы, срок — до удаления чата пользователем | `CURRENT-STATE.md`, «Карта хранилищ» |
| Новый юнит и правило экрана | эталон развёртывания: сверка покажет расхождение, пока эталон не пересняли |

Как именно эталон и генерируемые таблицы vLLM учитывают службу из другого репозитория, выясняется в начале этапа 1 (раздел 19).

**Правила сервера, которые нельзя нарушать при установке:**

- правки `ufw` — только под отложенным откатом (`systemd-run --on-active=10m ufw --force disable`) и с проверкой новым SSH-подключением;
- `setup-ai-stack-final.sh` на сервере не запускать;
- новый порт — ниже 32768 и не из забронированных (31009, 31014);
- привилегированные действия над службами сервера — только через `ai-ctl`; ключ клиента шлюза выпускает `ai-ctl gateway-key create`;
- значения ключей не попадают в файлы репозитория и в вывод сессии.

## 16. Ошибки

| Ситуация | Поведение |
|---|---|
| Исключение в слое распознавания, в сопоставлении или в построении текста | Очистка прервана, элемент `failed`, результат не выдаётся |
| Локальная модель недоступна при включённом слое 5 | То же; пользователь может явно отключить слой для чата |
| Проверка утечек нашла оригинал | Выдача и отправка заблокированы; показано, что и где найдено |
| Тип с политикой «блокировать» найден в тексте | Копирование и отправка заблокированы до удаления фрагмента |
| Ошибка провайдера или обрыв потока | Показана пользователю; полученная часть ответа сохранена и помечена как неполная |
| Файл не разобран | Элемент `failed` с причиной |
| Главный ключ не читается при старте | Служба не запускается и сообщает причину |

Сообщения об ошибках для пользователя и записи логов не содержат текста сообщений и оригиналов (SEC-11); исключения логируются по типу и месту, без значений переменных.

## 17. Тесты

Правила проекта: `pytest` без параметров — быстрый набор до 60 секунд; всё, чему нужны модели, документы, локальная LLM или сеть, помечается `integration`; запускаемое вручную — `manual`; предел 30 секунд на тест; время только подставное (`clock.py`). Команды запуска объявляются в `CLAUDE.md` проекта.

| Набор | Что проверяет |
|---|---|
| Быстрый | Правила и контрольные суммы на действительных и недействительных номерах; секреты по контексту; разбор адресов и имён; объединение фрагментов; канонические ключи; свойства перестановки адресов (сохранение префиксов, обратимость); подмены хостов; восстановление, включая регрессии из раздела 7 и разрез потока в каждой позиции; проверка утечек; шифрование и стирание ключа чата; права доступа к чужому чату; тест импортов (SEC-1); отсутствие оригиналов в базе, логах и журнале на контрольном прогоне |
| `integration` | Модели слоя 4 на контрольных текстах; Docling и распознавание текста на контрольных файлах; локальная модель; адаптеры протоколов против сервера-заглушки |
| `manual` | Запрос к настоящему провайдеру; замер скорости для NFR-4 |

Быстрый набор обязан проходить и на Windows (разработка, Python 3.14), и на Linux (сервер, Python 3.12). Отдельный тест разбирает исходники пакета как код Python 3.12 и ловит синтаксис новее целевой версии. Сценарии `deploy/` проверяются на сервере скриптом `check-cleaner.sh`, в быстрый набор не входят.

Измерение качества (`eval`) — не тест, а отдельная команда: её результат сравнивается с порогами QA-3 и с предыдущим замером (QA-6).

Контрольные данные в репозитории — только вымышленные. Эталонный набор из настоящих текстов хранится в базе на сервере и в репозиторий не попадает.
